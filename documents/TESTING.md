# Testing

**Scope:** What the pull request checks verify in this repository, and what the module's tests cover on which targets.

The organization's testing standard, `https://github.com/noldova-com/.github/blob/main/standards/TESTING.md`, applies here in full.

## The pull request checks

Every pull request into `main` must pass these three checks before it merges.
They run in GitHub Actions, where the organization's variables say, as the `.github` repository's README explains under "Shared settings".

| Check | What it verifies |
|---|---|
| Check / Linked issue | The organization's shared check, `linked-issue.yml` in the `.github` repository, which `.github/workflows/require-linked-issue.yml` calls from its `check` job, named "Check": the PR description has a standalone `Issue: #N`, `Issue #N` or closing reference, such as `Closes #N`, that names an issue in this repository. |
| Build and test / All targets | Every target's job passed. |
| Build and test / All shells | Every Shells job, which [The targets](#the-targets) describes, passed; the shared workflow's "All targets" doesn't wait for them, so this job of the caller's does. |

`.github/workflows/build-and-test.yml` calls the organization's shared `build-and-test.yml`, pinned to a commit of the organization's `.github` repository, whose comment names its release, with `publishes: true`, as the `.github` repository's README describes it.
Each target's job builds, checks the toolchain, Node.js 26.13.1 with npm 11.20.0, and the line endings, `* text=auto eol=lf` in `.gitattributes` and LF only with exactly one final newline in every tracked text file, with the shared pipelines tool, then runs `npm run test -- --skip-test-details --skip-coverage-details` and checks that the build and the tests changed no tracked file.
On Linux x64 it also builds a second time in a clean worktree and checks that the archives are the same, byte for byte, and on every target it checks the archives as the release does, with `pipelines archive`: each archive's name, version, `gitHead`, scope and licence, and a byte-for-byte copy of every file `npm run build --silent -- --list-copies` lists, at its path.
`npm run build` first installs the root's dependencies, which hold every package the three packages build and test with, with `npm ci --ignore-scripts` when `node_modules` is missing, so node-pty loads from its prebuilds, as an app's install takes it.
A full `npm test` ends by installing the packed packages from `_packages` into a fixture app with install scripts off, where the runtime part opens a terminal, runs a command whose answer the typed line doesn't hold and closes it at the next prompt, failing when the part logs that the shell didn't end in time, with `scripts/tests/installed-package/install-and-open.ts`, so it needs `npm run build` first. npm installs it with its peer checks on, so a peer the installed packages don't meet stops the install. The fixture app also installs Noldova Desktop's runtime, the module package's peer, and the six packages it depends on, packed from the repository's own install, so every context package is the version the repository installs and none comes from the registry at another one, and the `@types/node` version the root pins. It first compiles, with the library checks on, a module's call for the owners service and its own script against the installed declarations. Its context is Noldova Desktop's `FakeRuntimePartContext`, typed as `IRuntimePartContext`, which starts the part's programs and pseudo-terminals through Noldova Desktop's own `ProcessSupervisor` over a database in a temporary folder; it sends each request as the app's connection, waits for the `terminal.output` event that carries the answer and the next prompt, and checks that the part registers its agent tools and withdraws them when it deactivates. Off CI, it removes its temporary folder when it ends.
`--skip-test-details` gives the root suite Vitest's dot reporter and has context.testing's runner leave out the protocol's passing tests, and `--skip-coverage-details` leaves fully covered files out of its coverage table; `npm test` refuses any other option.
`npm run build` first fails when `npm ls @angular/cdk --all` at the root lists more than one copy, naming each copy's version and path, or none, with `scripts/checks/cdk-copy-check.ts`; a second copy, which npm nests under the UI kit without a warning when the window part pins another version, would run the kit's overlays and focus handling apart from the window part's. It then empties `_build/compiled`, so a removed source's script never reaches a pack, and builds the packages in the order they import each other, installing the archives packed so far with `npm install --no-save` after each pack: the protocol with the TypeScript compiler, the window part with Angular's compiler in partial compilation mode, then the runtime part with the TypeScript compiler, and checks the archives, failing on any finding ([ARCHITECTURE.md](ARCHITECTURE.md#the-package)).
`npm test` runs `scripts/test.ts`, which stops at the first step that fails.
It first runs the archive age check, `scripts/checks/archive-age-check.ts`, in every `npm test`, a filtered run too, which fails, naming `npm run build`, when a package's archive in `_packages` is missing or older than a file the build packs it from: the root's `LICENSE` and `tsconfig-base.json`, the package's `package.json`, `README.md` and `tsconfig.json`, everything under its `src`, and the module's `module.json`, `menus.json`, `settings.json`, `cli.json` and `webViews.json` where they exist. The tests use the installed archives, so without it a test of an edited package would run the archive packed before the edit. `npm run build` stamps each archive with the time the build started, so a file saved while it compiled or packed counts as newer, and a build that fails after it starts packing removes `_packages`, so no archive stays newer than the packages installed.
Next the declaration check, `scripts/declarations/declaration-check.ts`, runs in every `npm test`, a filtered run too, which fails on any problem in the repository's own `module.json` and the parts' and root's manifests: the declaration's fields and names, `pseudoTerminals` as `true`, with the tools' names as Noldova Desktop takes them, snake_case after `terminal_`, that its `dependencies` is an object from module ids to exact versions, the package's name, its version written `__VERSION__`, which packing sets to `version.json`'s, and its private flag, that every entry of `dependencies`, `devDependencies` and `optionalDependencies` is pinned exactly, but the module's own packages, which the module package names at `*` and packing sets to the module's version, that `noldovaDesktop` runs from a version to the next minor below 1.0, or the next major from 1.0, that the package's `peerDependencies` on Noldova Desktop's packages name it and its others an exact version or, on context's and the kit's packages, a range of the same form, that the root's development pins of Noldova Desktop are inside it, that the root's manifest pins no runtime `dependencies`, which the packages pin for themselves, that the root's `devDependencies` pin every dependency the module's and the window's manifests pin, at the same version, and that no part's manifest, the module's, the protocol's or the window's, pins a `@noldova` package but the module's own in `dependencies`, `devDependencies` or `optionalDependencies`, since the root pins those once, so moving one to its newest version leaves no older copy under a part's folder.
Then the test-wait check, `scripts/checks/test-wait-check.ts`, which Noldova Desktop's own check is the source of, refuses a fixed pause in any test file under `src` and `scripts`, a file in a `tests`, `e2e` or `fixtures` folder or a `*.spec.ts`, that README.md's Fixed pauses table doesn't list with its reason, and a listed file that no longer pauses: an import from `timers/promises`, `scheduler.wait`, `Atomics.wait`, `waitForTimeout`, or a `setTimeout` with a named callback or a number delay, or `requestAnimationFrame`; a test waits for the code's own event or promise instead. In the window part's test files it also refuses a `vi.waitFor` or `expect.poll`, with or without a type argument such as `vi.waitFor<T>(`, that would wait on the 1-second default: one with only its check, and one whose options, written in place as an object, have no `timeout` key, such as `{ interval: 1 }`. The check can't see what a named options object holds, so it passes one such as `SOON` on its name, and that constant must hold the limit itself. The scripts have no tests of their own, so every run of the check is what shows it works. Its logic, run over main's window files before this rule, named the 287 calls that took no options.
The API declaration check, `scripts/checks/api-declaration-check.ts` with `scripts/api`, ported from Noldova Desktop's, compares each package's exported surface with its `src/api/index.d.ts`, member by member, and fails on a member the code has and the declarations miss, or the other way, and on the declarations' own compile errors.
The example check, `scripts/checks/api-example-check.ts`, compiles the code of every `@example` in those declarations against them, in memory, and fails on each compile error, with its file and line.
The build reads only the window part's one copy, so no run shows the copy check failing.
It then type-checks the repository automation under `scripts` and the window part's under `src/noldova.terminal.window/scripts`, and the module's source and tests by its `tsconfig.spec.json`, with the TypeScript compiler.
Then `scripts/testing/test.ts` runs the protocol's tests, as context's `scripts/test.ts` runs context's, from the files it imports from CONTEXT into `scripts/testing`: it refuses an option it doesn't know, compiles the tests with `src/noldova.terminal.protocol/tests/tsconfig.json` into `_build/tests/noldova.terminal.protocol.tests`, which type-checks them against the installed package's declarations, runs every test class there with `@noldova/context.testing`'s runner, with Node's V8 coverage written to `_build/protocol-coverage` and each test's time to `_build/tests/test-results.json`, prints the 10 slowest tests, and fails unless context.testing's coverage analyzer finds the installed package's code, `node_modules/@noldova/terminal.protocol/src`, wholly covered, or fails with the analyzer's message when it can't measure it. The tests import the protocol as `@noldova/terminal.protocol`, the archive `npm run build` installs, so they run the code that ships: the tests' `tsconfig.json` maps that name to the installed `src/api/index.d.ts`, since the protocol's own manifest would otherwise resolve it to its sources. Every `.js` file of the installed package counts, so a file no test loads fails the gate; the archive holds no source maps, so the coverage table names the `.js` files. `tests/api/index.test.ts` checks the package's export list. A test compares objects with `Expect.same` in `tests/support/expect.ts`, through Node's `isDeepStrictEqual`, and checks a thrown error's fields with `Expect.throwsMatching`.
It then runs every `*.test.ts` file under the `tests` folder of the module's package with Vitest. A full run writes Vitest's JSON report to `_build/test-times.json`, and `scripts/checks/test-time-check.ts` then names each test file that took over 1 second in that run, and whether README.md's Test files over 1 second table accepts it; it fails only when the report names no test file with its times, since a gate's pass condition is never a time.
`npm run test:timing`, `scripts/timing/timing-check.ts`, is the timing check, apart from `npm test` and run on a quiet test machine: it runs the root's test files, the window part's specs and its look specs, `ng run window:test-look`, three times each, takes each file's time, and each spec's tests' times, as the median of the three runs, so one run slowed by a busy machine doesn't decide it, and fails on a unit test file over 1 second that README.md doesn't accept, or a spec file whose median test is over 100 milliseconds that README.md doesn't accept, each only past its bar plus 20% for the jitter a quiet machine still has; it also names each component test over 1 second, whose spec README.md lists with its cause, and fails when a run's report names no file with its times or README.md lacks either table. Then it runs `scripts/testing/test-timing.ts`, from CONTEXT's `scripts/test-timing.ts`, which runs the protocol's tests, as `npm test` last compiled them, three times and has context.testing's `TestTimingCheck` judge each file against a 2-second budget with a 50% margin, failing when one is over or a run fails.
Last it runs the window part's tests itself, with `src/noldova.terminal.window` as the working folder and each tool's script from the root's `node_modules`, in three steps: the preparing step, where `ngc --project tsconfig.json` type-checks the part and `playwright install --only-shell chromium` installs the browser, then `ng test`, where Angular's unit-test builder runs every `*.spec.ts` under `src/noldova.terminal.window/tests` with Vitest in headless Chromium through Playwright, with real xterm, real layout and WebGL through SwiftShader, against a fake window context and a fake runtime. The part's `vitest.config.ts` has Vite pre-bundle context's three packages before the first spec loads, so the test page holds one copy of each, which the specs and the protocol both import, since `@noldova/context.core` refuses to install its extensions twice.
The same config sets Vite's cache folder to `_build/window/vite` from a plugin's `config` hook rather than its top-level `cacheDir`, since Angular's unit-test builder passes its own cache folder in the server config, which overrides the config file's, and Vite merges a `config` hook's result after both; the root's `vitest.config.ts` keeps its cache in `_build/vite`. Nothing empties them: Vite pre-bundles again when the lockfile or the config changes, and a last `config` hook takes `@noldova/terminal.protocol` out of the packages Angular's builder has Vite pre-bundle, so the specs load the protocol's source as it is; a pre-bundle of it would keep its old code, since neither the lockfile nor the config changes with it.
Then `ng run window:test-look` runs the look specs, every `*-look.spec.ts` under `src/noldova.terminal.window/tests`, which the unit target leaves out, as their own target on a build with the kit's stylesheet, since the builder links a build's stylesheet on every test page, and saves their screenshots under `_build/window/screenshots`, outside the repository.
`terminal-panel-look.spec.ts` draws the panel in the kit's light and dark looks, and turns forced colors on and off while the shell runs, checking that the panel, the pane and the cells xterm draws take the system's Canvas, and then that the panel and the pane paint nothing again and xterm draws on the window's background. It places the panel on the kit's window and panel colors in light and dark mode and checks that xterm's empty cells draw in that color and that each of the 16 ANSI colors, drawn as a glyph at 40 pixels, has a pixel at a contrast of at least 4.5 with it. In light and dark mode, under the kit's default theme and its test theme, it also checks that the pane's text, and the cursor, selection and selection text color it gives xterm, are the theme's terminal tokens, and that the focused cursor draws in the cursor color; in forced colors the same check finds the system colors the kit's kit.css gives those tokens, and HighlightText as the selection text color. Two red squares, selected in forced colors under each theme, then draw in HighlightText instead of their own color, on Highlight laid over Canvas as xterm lays a focused selection. Selected with forced colors off, they take those colors once forced colors turn on, and the colors they had once they turn off; squares, since xterm half blends a selected box or block glyph's own color with the selection instead. In light and dark mode under each theme, the same squares, once drawn, hold none of the theme's terminal selection text color, and selected they draw in it as xterm draws it on the theme's selection, which a reference line of squares drawn in that pair shows: the color itself where it meets 4.5:1 there, as the default theme's does, and raised to 4.5:1 where it falls short, as the test theme's does. The selection then runs from the selected line's top edge to its bottom edge and to its last cell, and stops at the line below.
`terminal-pane-appearance-look.spec.ts` changes the code font and Code text size, the panel text size, the mode and the theme through the kit's appearance service while the pane is out of the page, as a tab behind another is, and compares the pixels the pane draws with the terminal background and the theme's colors, its background with the window's, which the panel and the pane don't paint over, and its text size with the Font size setting's default 13 pixels before and after each change, and its cell size and the shell's columns with the new font at 13 pixels after the panel and Code text sizes change.
A look spec that waits for the screen to show a color reads it through `DrawnWait` in `src/noldova.terminal.window/tests/fixtures/drawn-wait.fixture.ts`, one wait with one generous limit, 10 seconds. One screenshot takes over a second on a loaded machine, and the two look files take theirs in one page at the same time, so the limit only bounds a hang. Every other wait in a look spec, such as for a pane's size, an acknowledgement or a list, passes `{ timeout: DrawnWait.milliseconds }` to `vi.waitFor` too, since `vi.waitFor`'s own limit of 1 second ran out on a slow Linux machine before the pane had drawn. A wait that runs out names what it waited for and the colors it last read. `terminal-pager.spec.ts`, which pages thousands of stored lines into a real xterm as the pane scrolls, waits the same way: its waits for the pager's lines pass `{ timeout: DrawnWait.milliseconds }`, since the lines arrive only after the page's request is answered and xterm has parsed them.
Every other `vi.waitFor` and `expect.poll` in the window part's specs has a limit of `SpecWait.milliseconds`, 10 seconds, from `src/noldova.terminal.window/tests/fixtures/spec-wait.fixture.ts`, which `DrawnWait` takes its limit from too. Their own default of 1 second ran out on a slow macOS x64 runner before a typed key's input was sent (#29). A longer limit only slows a wait that fails.
`terminal-session.component.spec.ts` checks its waits every millisecond, with `SOON`, `{ interval: 1, timeout: SpecWait.milliseconds }`, rather than at `vi.waitFor`'s 50: each of its tests attaches a pane, which sends its size a frame later, and a 50 millisecond check took half of each test's time on the Linux test machine.

Each suite has one hang limit, for each test and each hook, and no test or `describe` sets its own; each is at least three times the suite's slowest test on any target, measured on the test machines from full runs of `npm test`, and is never raised to make a slow run pass: a test that reaches it is a bug to fix, and Vitest names it and the limit it reached.

| Suite | Limit | Where | Slowest test |
|---|---|---|---|
| The module's tests | 70 seconds | `src/noldova.terminal/vitest.config.ts` | 22.1 seconds on the Windows test machine: `one-shot-command.e2e.test.ts` runs a command after each developer shell's start and in each WSL distribution. |
| The protocol's tests | context.testing's default, 30 seconds | `@noldova/context.testing`'s runner | 18 milliseconds on the Linux test machine, a `TerminalRunParams` test; the whole run took 0.4 seconds. |
| The window part's specs, the unit and the look specs | 30 seconds | `src/noldova.terminal.window/vitest.config.ts` | 3.5 seconds on the Linux test machine in a full run, a `terminal-pager.spec.ts` test, which took 2.2 seconds on the macOS test machine and 1.5 on the Windows test machine in the timing check's runs, where the slowest look test took 1.5 seconds on each; it is also above `DrawnWait`'s 10 seconds, so a wait that runs out reports what it waited for before the test's limit ends it. |

The shell integration tests live in `tests/fixtures/shell-integration-suite.fixture.ts`, and one file for each shell runs them, `tests/services/shell-integration.<shell>.e2e.test.ts` for bash with sh, Git Bash, zsh, PowerShell 7, Windows PowerShell and Command Prompt, so Vitest runs the shells on separate workers at once. A test that writes a PowerShell's real `$PROFILE` runs in that PowerShell's file, since two files writing the same profile at once would each find the other's. They wait up to `SHELL_COLD_START_MS`, 55 seconds, for each new shell's first prompt mark, and 20 or 40 seconds for its other marks. A wait fails at once when its shell ends first, naming how it ended and its exit code, so a shell that fails to start, as PowerShell 7 sometimes does on macOS when its own startup's `sysctl` read of its arguments fails with `procargs` errno 5 (PowerShell/PowerShell#20802), fails as that rather than as a missing prompt mark 55 seconds later. On 2 fresh hosted Windows arm64 runners, in a 10-run Flake proof of these six files, which start their Windows shells at once, the job's first Windows PowerShell test with profiles took 34.7 and 36.5 seconds in all, its first prompt among them, against 2.6 to 3.1 seconds in the 8 later runs there, so the wait leaves that test at least 33 seconds under the suite's 70-second limit. The test of a shell's nonce file runs in the bash file on Linux and macOS, and on Windows in the Windows PowerShell file, after its shell tests, so its `Get-Acl` check starts a Windows PowerShell once the job's first has run: it took 1.0 to 1.3 seconds in every run of that proof. As the bash file's only test on Windows, it started the job's first Windows PowerShell alongside the other files' shells, and took 56.5 and 59.2 seconds of its 60 on fresh arm64 runners.

`tests/runtime-part.e2e.test.ts` waits up to 20 seconds for each output or event it names, and up to `RUN_WAIT_MS`, 55 seconds, for each `terminal.run` to answer, the same as a new shell's first prompt above, since a Run into a new shell waits for that prompt. Each test's fixture also sets a deadline, `TEST_DEADLINE_MS`, 65 seconds after it is made, and a Run waits only for what is left of it when that is less, so a later Run in a long test still fails before the suite's limit. A Run that doesn't answer in time fails the test with each terminal's marks and the end of its output, so a Run that hangs shows what its shell sent instead of reaching the suite's 70-second limit with nothing to read.

On Linux, the end-to-end files start several pwsh at once, which on a fresh hosted runner, whose runtime folder has no `.dotnet` yet, can meet .NET 10's race in making its shared memory folder (#7). They need no setup of their own for it: the runtime makes `$XDG_RUNTIME_DIR/.dotnet/shm` before the first pwsh starts, as [Starting a shell](ARCHITECTURE.md#starting-a-shell) says. `tests/services/shell-integration.test.ts` checks that step, since the race is rare and an end-to-end run almost never shows the step missing; a pwsh in an end-to-end file's output that draws no prompt marks, with `mkdirat(...) == -1; errno == ENOENT` from PSReadLine's history mutex, means the step didn't run.

The automation under `scripts` has no tests of its own, as the organization decided for every repository: the packages it builds are tested, and nothing measures it.
Arguments make a filtered run, as `npm test -- <test file>` does.
A window spec, named from the repository root with forward slashes, such as `src/noldova.terminal.window/tests/app/components/terminal-panel/terminal-panel-look.spec.ts`, runs alone in the window part after the preparing step: a look spec through `ng run window:test-look --include <spec>`, any other through `ng test --coverage=false --include <spec>`.
A file under `src/noldova.terminal.protocol/`, such as `src/noldova.terminal.protocol/tests/models/terminal-size.test.ts`, runs through the protocol's step, which passes its name without `.ts` to context.testing's filters, so the test classes compiled from a file of that name run, without the coverage gate.
Vitest takes the other arguments as the root suite's filters and still measures coverage, so a test runs as slowly as in the whole suite, but the coverage gates are off, since only the whole suite can meet them; the root suite runs only when such an argument is given, and a filtered run is not the gate.

## Coverage

`npm test` without arguments measures the module's coverage with Vitest's V8 coverage and the protocol's with context.testing's coverage analyzer, and fails below 100% of the statements, lines, branches and functions.

| Scope | Requirement |
|---|---|
| The package's production code under `src/noldova.terminal` | 100% of lines, branches and functions. |
| The protocol's production code under `src/noldova.terminal.protocol/src` | 100%, measured by context.testing's coverage analyzer. |
| Repository automation under `scripts/` and `src/noldova.terminal.window/scripts/` | Not measured: it has no tests of its own; the packages it builds are tested. |
| Test files, the files under each `tests` folder | Not measured: they are the tests, not the code under test. |
| Third-party packages under `node_modules` | Not measured. |
| JSON declarations and manifests, and YAML workflows | No coverage percentage; the declaration check under `npm test` checks `module.json` and the manifests, and the workflows' own runs check the YAML. |

The coverage leaves out only what the README's [Checks](../README.md#checks) section grants, each with its reason: the window part, the protocol, which its own tests measure, and each package's `vitest.config.ts` in the root's coverage, and the window part's enum files and the compiler's class-metadata calls in the window part's.
The root's coverage includes every other `.ts` file under `src` outside the `tests` folders, so a file that no test loads counts as uncovered and fails the gate.
The window part's specs measure `src/noldova.terminal.window/src` the same way, through the unit-test builder's V8 coverage, without the files under `src/app/enums` and the compiler's development-mode class-metadata calls, which `src/noldova.terminal.window/tests/coverage/class-metadata-coverage.ts` marks and counts.

"Build and test / All targets" also runs on every push to `main`.

## The targets

The module's tests run on Linux x64, Windows x64 and macOS arm64 for every pull request, draft or ready, and on all six targets, Linux, Windows and macOS on x64 and arm64, for every push to `main` and every run started by hand, on GitHub-hosted runners; the jobs check the toolchain, not the runner's platform and architecture.
Pull requests skip Linux arm64, Windows arm64 and macOS x64.
The workflow's first job, `build-and-test`, named "Build and test", calls the shared workflow, which runs one job per target, named for its target, such as "Linux x64", which GitHub lists as "Build and test / Linux x64", and its "All targets" fails unless every one of them passed.
The caller follows context's, `.github/workflows/build-and-test.yml` in the context repository, except in two ways: a pull request runs only the three targets above instead of context's six, and it sets `timeout-minutes: 20`, so a job that hangs fails after 20 minutes.
Each target's job builds, checks the toolchain and the line endings, tests, opens a terminal from the packages installed into a fixture app, and checks the archives.

The shared workflow has no step that installs a program, and GitHub's Linux image doesn't promise zsh or fish, so the workflow's second job, `shells`, named "Shells", tests them on Linux x64 and macOS arm64, and on Linux arm64 and macOS x64 too for a push to `main` or a run started by hand, in its own steps: on Linux its step "Install zsh and fish on Linux" installs both with apt, and its step "Make zsh's completion folders safe on Linux" removes group and other write from each folder zsh's `compaudit` names, printing them, and fails when `compaudit` still names one, since Ubuntu's `/etc/zsh/zshrc` runs `compinit`, which would otherwise ask about them before zsh's first prompt, and its step "List the job's shells in /etc/shells on Linux" adds each of the job's shells that `/etc/shells` doesn't list, since the terminal offers the shells that file lists and the Linux arm64 image's PowerShell isn't in it; on macOS the image's zsh is used. It fails when the runner lacks one of the job's shells, bash, PowerShell 7 and zsh, with fish on Linux. Its step "Install the packages" runs `npm ci --ignore-scripts`, and once more after 30 seconds, with a warning naming the code, only when npm's output names a network error code, such as `ECONNRESET`, `ETIMEDOUT` or `EAI_AGAIN`, since a reset connection to the registry failed the step once (#31); any other failure fails the step at once. Its step "Build and install the packages" runs `npm run build`, which packs the three packages and installs their archives, since the tests import the protocol and the window as installed packages. The job then runs the module's end-to-end files that open shells, `runtime-part.e2e.test.ts`, the shell integration files of its shells, `shell-integration.bash.e2e.test.ts`, `shell-integration.zsh.e2e.test.ts` and `shell-integration.pwsh.e2e.test.ts`, `shell-integration.pwsh-login.e2e.test.ts`, which starts a stand-in pwsh through `/bin/zsh` as a login sh as macOS's pwsh starts, and whose test is tagged for no shell, so it may skip where `/bin/zsh` is missing, `pseudo-terminal.e2e.test.ts` and `shell-locator.e2e.test.ts`, and `scripts/checks/shell-run-check.ts` fails when a test tagged for one of those shells didn't pass, a skip included, or none did.
A test's title carries a shell's tag, such as `[zsh]`, when that shell's being installed is the only condition it runs on, so a test that skips on a platform by design, such as PowerShell's execution policies off Windows, carries none.
The job "All shells" fails unless every Shells job passed.

## What the tests cover

On every pull request, on every target:

- Unit tests, with named fakes for the pseudo-terminal that record writes, sizes, kills, pauses and resumes, for the fit and WebGL addons, and for the browser APIs the pane uses: resize observation, media queries, fonts and the clipboard.
- The window part's specs in headless Chromium: attach and replay, acknowledgements, detach and reattach, fit, the WebGL renderer and its fallback after a lost context, key routing, copy, paste, links, the ended strip, the theme, the cursor accent, and the fallback palette's approved colors in both modes.
- Integration tests of node-pty in a real shell: an echo round trip, a resize, the exit code, a polite end followed by a forced kill, no child process left behind, and 4 MiB of output, four times the 1 MiB high watermark, under flow control.
- The shells: bash and PowerShell 7 everywhere and cmd on Windows, in each target's job; zsh on macOS and Linux, and fish on Linux, in the Shells job above.

By hand, on native machines:

- IME composition in Japanese, Chinese and Korean on Windows and macOS.
- Paste through the operating system's clipboard: bracketed, large and multi-line.
- The signed and notarized build loads the native addon under the hardened runtime and its entitlements, after Gatekeeper's quarantine and SmartScreen.
- Install, update and quit, after which no shell, conhost or OpenConsole process is left, also after the installed app crashes.
- The WebGL fallback on virtual machines.
- Resizing while large output streams, at display scaling from 100 to 200%.
- GNOME and KDE desktop sessions on Linux.
- Windows, elevated and not elevated.
