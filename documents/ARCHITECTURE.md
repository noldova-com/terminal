# Architecture

**Scope:** What Terminal is, as a module and as an app of its own, its parts and the packages it builds on, the maintainer's decisions it keeps, and where its boundaries with Noldova Desktop and the apps that include it lie.

This document describes the code as it stands.
**Not yet** marks what waits for Noldova Desktop, for the components repository or for a decision, as [Dependencies](#dependencies) lists.

## The boundary

- Terminal is a module, with the id `terminal`, for any app on [Noldova Desktop](https://github.com/noldova-com/desktop), and an app of its own built on Noldova Desktop.
- It stays product-neutral: an app adds its packages and configures them through their published API, and no app's names, text or behavior live in it.
- It installs published versions of Noldova Desktop's packages and `@noldova/ui.components.angular`, and depends on no app.
  An app asks for a change to Terminal through an issue here, and Terminal asks for a change to Noldova Desktop or the kit through an issue there.
- It runs on Windows and Linux on x64, and on macOS on x64 and arm64, the targets its CI checks.

## Its forms

### The module

The module follows Noldova Desktop's module contract, `documents/MODULES.md` in Noldova Desktop.

- `module.json` declares the id `terminal`, the parts `runtime` and `window`, and the `terminal.*` methods and events it contributes, with the window part's commands `terminal.new`, `terminal.newWithShell`, `terminal.toggle` and `terminal.restartShell`, its views: the panel `terminal.panel` and the terminal tabs `terminal.session`, the menu places `terminal.tabRow` and `terminal.shellMenu` that `menus.json` fills, with the groups `terminal.tabActions` it adds to Noldova Desktop's tab menu `desktop.tab` and `terminal.viewActions` it adds to the View menu `desktop.view`, the settings `terminal.defaultShell`, `terminal.outputLimit`, `terminal.fontSize`, `terminal.suggestions`, `terminal.commandColors` and `terminal.completionList` that `settings.json` declares, and the agent tools from `terminal_list` to `terminal_close` ([The agent tools](#the-agent-tools)).
- The runtime part runs in the app's runtime and owns every terminal's shell, and publishes the agent tools ([The agent tools](#the-agent-tools)).
- The window part shows the panes, as views of the module, edge to edge, as Noldova Desktop lets a terminal page turn its padding off.
  Keys a pane handles stay with it, as Noldova Desktop leaves a key a terminal handled alone.
  An app can show a pane in its own page too, with `EmbeddedTerminal` ([INTEGRATION.md](INTEGRATION.md#showing-a-terminal-in-the-apps-own-page)), which gives the pane's rows drawn and its row height, measured from xterm's screen, so the app sizes it in rows without the pane's inset.
  Within a window, one pane of a session sizes its shell, the shown one the person focused last, else the shown one opened last, so a pane that opens takes it from no pane the person has focused, and the others draw at its size (`SessionSizing`), so two panes of one session never resize it back and forth.
- The two parts exchange only the messages of the protocol part, over Noldova Desktop's local protocol.

### The app

Terminal is also an app on Noldova Desktop whose only module is `terminal`.

- Its root `package.json` will declare the app's identity under `desktop.product` and list `terminal` under `desktop.modules`, as Noldova Desktop's `documents/BUILD.md` says.
- A person will open terminals in the app's window; the window, the main process, the runtime and the command line will be Noldova Desktop's.
- The app has no agents of its own, so it will serve no agent tools; its terminals are the person's.
- **Not yet:** the root `package.json` has no `desktop` section; the app's identity is the maintainer's decision.

### The module in an app

An app includes the module from its installed packages, pinned exactly, and lists `terminal` in `desktop.modules`.

- Noldova Desktop's build reads the module from its installed package, as [INTEGRATION.md](INTEGRATION.md#pinning-and-listing-the-module) says, and the app never copies or patches Terminal's code.
- The app's agent host serves the agent tools to its agent sessions, and bind to each session its working folder and the terminals the person shared with it.
- The app owns the permission card the person answers and the policy that decides which requests need it; Terminal owns its tools, the risk of each and what each request shows and binds.
- Until the app registers its answerer, Noldova Desktop denies every request, so only `terminal_list` works ([The permission request](#the-permission-request)).

## The maintainer's decisions

These decisions hold, and this table says how the code stands against each.

| Decision | What it says | The code now |
|---|---|---|
| A terminal belongs to the connection that opened it | Only that connection gets the terminal's output and types into it, and the terminal ends when the connection closes: quitting or a crash ends it, and a reload keeps it. The command line, which agents can run, never reaches a person's terminals. | Done, with the agents' terminals decided on 2026-10-21: an agent's terminal can belong to its chat, so the person watches it, types into it and closes it, and the app's connection reaches it ([Connections](#connections), [Which terminals an agent reaches](#which-terminals-an-agent-reaches)). The command line, a connection of its own, reaches only the terminals it opened. |
| Clear clears the stored lines | `clear` or `cls`, which erase the saved lines or reset the terminal fully, also clear the lines stored for the terminal. | Done in the runtime: erasing the saved lines of the normal screen, or a full reset, clears the terminal's stored lines ([Stored lines](#stored-lines)). An agent's text keeps up to 2,097,152 UTF-16 code units apart from them. |
| Restart keeps the old output | The old screen joins the stored lines, and the new shell starts below them. | The new shell starts below the old screen, which scrolls up into the scrollback, as [Restarting a shell](#restarting-a-shell) says, and on into the stored lines as later output pushes it out; a restart keeps the stored lines. |
| TerminalList | A `TerminalList` method lets a reloaded window find its terminals. | The `terminal.sessions` method lists the terminals the asking connection reaches ([Connections](#connections)). |
| Windows reads the fresh environment with `reg export` | Each read exports the two Environment keys to UTF-16 files, which keep non-ASCII text, rather than keeping a Windows PowerShell running for it. The registry's values overlay the app's inherited environment, so a deleted variable lingers until the app restarts. A registry read in Noldova Desktop would need no files; it is a later issue. | Done, as [Starting a shell](#starting-a-shell) says. |

Decided with them:

- Each shell gets a fresh environment from the operating system.
- A terminal's output is stored under `terminals/` in the data directory, deleted with the terminal, cleared when the runtime starts, and never put in a database backup.

Still open: the stored lines sit in the system's temporary folder until a part has a data folder of its own, and move there then ([Stored lines](#stored-lines)).

It then packs each package into `_packages`, building it in `_build/packages/<package folder>`, such as `_build/packages/noldova.terminal.window`.

`.github/workflows/release-npm.yml` releases the packages to npm through the organization's shared npm release, v2.34.0, with npm's trusted publishing, so no token is stored: each package's trusted publisher on npm is this repository's `release-npm.yml` in the `release` environment.
A member starts it by hand on main with a version and the commit main is at, since the shared release refuses a run that started anywhere else, and the `release` environment's reviewer approves the publication.
The pull request that changes the version writes that version's section in [CHANGELOG.md](../CHANGELOG.md), from the pull requests merged since the previous version, and no other pull request edits the file.
The release never deletes a published version.
After the release, its dependents job calls the organization's shared `update-dependents.yml`, v2.34.0, with the version and the commit, in the `version-updates` environment, which holds the version-updates App's key and deploys from `main` only; each repository the App's installation includes that pins this module's packages exactly at an older version, such as the app, gets a pull request that moves the pins and refreshes its lock files, as the shared workflow's README says.
The shared release, the organization's `release-npm.yml`, it reads the version from `version.json`, checks that the commit is on main and holds that version, and tags the commit first, so a workflow change merged to main during the release can't leave the version untagged; it then runs `npm ci` and `npm run build`, checks the archives in `_packages` with its pipelines tool, which asks the build's `--list-copies` for the files it copies, and publishes them.
A build or publish that fails keeps its tag, so the same version can be released again from the same commit, but a fixed commit needs a new version.
`npm run build` refuses to pack when `version.json` or the root `package.json` holds a version other than `module.json`'s, so a version change moves all three.
It records the commit as each archive's `gitHead` only in a clone with no changes, as the release's clean clone is; a build from changed files records none, so its archives can't be released.
It empties `_packages` before packing, and after packing it checks the archives with `scripts/services/archive-check.ts`, failing on any finding.
The check refuses a folder that doesn't hold exactly the three archives at the version, and an archive whose name, version or own pins differ from the module's, whose `gitHead` isn't the commit the build recorded, or that lacks a file an export names.
It also refuses a module package without `module.json`, a pin or peer that isn't one exact version, other than a peer on context's or the kit's packages at a range of the one form `>=<lowest> <first refused>` and a peer on Noldova Desktop's packages, which takes the `noldovaDesktop` the module's `module.json` names, and a window package's peer that isn't optional.
`npm run build --silent -- --list-copies` builds nothing and prints each file the build copies into a package unchanged, which the shared release's `pipelines archive` compares with the archives from its tools 0.0.7 on: each line holds the source from the root, the package's name and the path inside the package, separated by tabs, and the last line is `end of copies`.
The copies are `LICENSE` and the package's own `README.md` in each package, whose links are absolute so they work on npm, and the module's own JSON files, such as `module.json`, at the module package's root; the declarations, which the build rewrites, and the compiled scripts aren't copies.
Any other option beside `--list-copies` fails the build.

## Permissions

- The module owns its actions and the risk level of each.
- The app owns the permission card the person sees and the policy that decides which requests need it.
- The permission contract routes each request to the part the app chose to answer it, and records the decision.
- An agent's command runs only after a decision allows it.

## The runtime part

The runtime part runs in the app's runtime process and owns every terminal's shell.
Windows reach a terminal only through the `terminal.*` methods and events the module declares; the protocol part holds their messages.
`terminal.open` opens the default shell when its `shellId` is null, and in the person's home folder when its `folder` is null or no longer exists; the runtime refuses a relative folder and one that is absolute only on another platform, and says in the module's log and the terminal's first line when a folder no longer exists. A terminal opened with such a note starts its shell below it. On Windows a shell with the integration prints the note itself, before the person's startup files, so the pseudo console paints it above the first prompt: the runtime hands it the note's lines, already styled and with their control characters replaced, in the `NOLDOVA_TERMINAL_NOTE` variable, which the script writes as it is and removes, so nothing in a folder's name runs; PowerShell 7 writes it through `Write-Host`, which leaves out its styles when `NO_COLOR` is set, and ConstrainedLanguage refuses any other way that keeps the text intact. Command Prompt, which has no integration, prints the note itself too. It starts with `/s /k`, whose line first has a second Command Prompt, with delayed expansion and without the AutoRun commands, echo the same variable. That one reads the variable only after it has split its own command, so the note stays data whatever delayed expansion the person's registry sets. Then the first clears the variable and runs what its `/k` ran before, such as VsDevCmd; the person's AutoRun commands still run first. A shell with neither, such as a WSL distribution, inherits the cursor below the note the runtime writes: the pseudo console asks the mirror where the cursor is, and paints from the top of the screen when the answer doesn't come within a second, which a loaded machine's slow start can outlast. An agent's terminal still refuses a folder that doesn't exist.
`terminal.sessions` gives each terminal's shell, folder, title and exit, whether an agent session owns it, whether it is the panel's, which `terminal.open`'s `isPanelTerminal` asks for, and its `owner`, which `terminal.open` gives. The runtime keeps one panel terminal for every window's panel: a panel open answers with the one it has, or with the one it is still opening, so panels that start together share it.
`terminal.attach` gives a pane the terminal's screen, title, exit and working folder ([Shell integration](#shell-integration)).
`terminal.lines` gives a page of up to 500 of the lines stored above the snapshot ([Stored lines](#stored-lines)).
`terminal.restart` starts a terminal's shell again in the same terminal, at the size of the pane that asks, and sends `terminal.restarted` ([Restarting a shell](#restarting-a-shell)).
`terminal.restore` opens again, once a run, the person's terminals the last run left open ([Terminals across runs](#terminals-across-runs)).
`terminal.closeOwner` ends the terminals tied to an owner and sends `terminal.closed` for each, as closing any terminal with an owner does, and `terminal.opened` tells the windows of an agent's terminal that opened with an owner, and of a terminal a run opened for its owner ([Terminals with an owner](#terminals-with-an-owner)).
`terminal.launch` opens an app's terminal with the app's variables over the shell's environment and a notice above its first output, and answers with its session, or with its folder when that no longer exists, opening nothing, since a request's failure reaches the window without its reason ([Terminals an app launches](#terminals-an-app-launches)).
`terminal.run` types an app's commands into a free terminal of an owner, or one it opens for them, and answers with that terminal and whether it typed them ([Running an app's commands](#running-an-apps-commands)).
`terminal.showOwner` tells the runtime which owner's terminals the asking window shows, or none with a null `owner`, and with `isHidden` whether the window is hidden; the window part sends it as the window starts, whenever the shown owner changes or the window hides or shows again, and again after the runtime reconnects, and sends a null owner with `isHidden: true` while the window is hidden, such as minimized, and the runtime keeps it for the window until the window or its connection closes ([Running an app's commands](#running-an-apps-commands)).
`terminal.rename` gives a terminal the person's name for its tabs, or takes it away with a null `name`, and sends `terminal.renamed` with a `TerminalName` to every window that reaches the terminal; `terminal.sessions` lists the name as `name`. A program's own title never changes it, and a kept terminal keeps it for the next run ([Terminals across runs](#terminals-across-runs)).
`terminal.complete` gives what can follow at the cursor of a bash, zsh or PowerShell line ([Completion list](#completion-list)).
`terminal.findCommands` gives which of the command names typed at a bash, zsh or PowerShell prompt the shell would find nowhere ([Command colors](#command-colors)).

### Connections

Each terminal belongs to the connection that opened it, as Noldova Desktop names its clients: the app's windows share the main process's connection, whose client is Noldova Desktop's `ShellClients.mainProcess`, and the command line has one of its own.
The runtime takes that name from `@noldova/desktop.protocol`, never a copy of it, so a request counts as the app's only when Noldova Desktop's main process sent it.

- A method about a terminal its connection doesn't reach is answered as if the terminal didn't exist, and `terminal.sessions` lists only the terminals the connection reaches.
- A terminal that doesn't exist, or that the connection doesn't reach, is refused as `NotFound`, which Noldova Desktop answers without logging a failure; `terminal.ack` and `terminal.detach` for it are answered as done, since a view may still send them after its terminal ended and was forgotten.
  A view that gets the refusal sends nothing more for that terminal, and detaches nothing when it closes.
- The app's connection also reaches the agents' terminals with an owner, so its windows show them; an agent's terminal without an owner is reached by no connection, and only its agent session uses it.
- A terminal's events go only to the windows of the connections that reach it, and to a connection without windows as a whole.
- A window that closes for good, or reloads, ends only the terminals it launched without a tab, which no other window shows, and keeps every other terminal: Noldova Desktop reports no closure for a reload, so Terminal's window part sends `terminal.windowStarted` as it activates, registering its views and commands meanwhile and serving a launch only once answered, and the runtime ends the launches without a tab of that window's earlier pages, never the asking page's own, waiting only for that window's launches under way.
- The runtime keeps each pane's connection, window and page from its attach, so it detaches the panes of a window's earlier pages when its next page starts, and every pane of a window that closes for good or a connection that closes: a page that goes away sends no `terminal.detach`, and a pane it left would count as shown and never acknowledge, pausing its shell for 10 seconds on the next 1 MiB of output until flow control detached it.
  The runtime keeps the pane's page from the attach's start, and a pane whose page or window left before its attach was done, as while the mirror parses a backlog, is detached once it is.
  A pane that closes while its attach is under way sends `terminal.detach` once the attach answers, since the runtime counts it from then.
- A connection that closes ends its terminals, with those its opens under way start, from their first step, without waiting for another connection's opens, and the app's also ends the agents' terminals with an owner, whether the app quits, crashes or its main process reconnects; the saved rows stay, so the next run restores the person's terminals.
- A reconnected app's restore waits for the old connection's close under way, so it restores the person's terminals that close ends.
  When its own connection closes during that wait, it restores nothing, and the next app connection restores them.
- Only the app's connection restores terminals, keeps the terminals it opens for the next run, and has a panel terminal of its own; another connection's panel open gets one of its own.
- `terminal.closeOwner` from a connection ends only the owner's terminals that connection reaches; only the app's connection, or the runtime service `terminal.owners`, also forgets their saved rows and unbinds the owner's agent sessions.

| Piece | What it does |
|---|---|
| Pseudo-terminal primitive | Starts the shell as a 256-color terminal in the chosen folder and size, below the cursor when asked, and ends it. Noldova Desktop owns it: `module.json` declares `pseudoTerminals`, and `src/noldova.terminal/src/services/context-pty-spawner.ts` starts each shell and one-shot command through the part's context with the module's own node-pty, with ConPTY's bundled build on Windows; `src/noldova.terminal/src/services/context-pty-process.ts` hands on its output, exit and stop. |
| Pseudo-terminal adapter | Turns the primitive's output and exit into the terminal's, ends a shell that exits by itself as it ends one it closes, drops input and resizes after the shell exits, and reports a signal's end, or an exit the primitive gives no code for, as no exit code. On ConPTY, once the shell's output asks for the cursor's position (`ESC[6n`), even across two reads, it holds the input until the headless mirror has answered every open request, one answer each, and writes it after the answers, or 500 ms after the latest request when no answer comes; the shell's exit drops what it holds. Only the mirror's answers, which the session writes apart from input, end a hold, so a typed key that looks like an answer, such as Shift+F3 (`ESC[1;2R`), doesn't. The pseudo console sends that request after every resize and drops a key that reaches it before the answer: on a Windows test machine, 1 of 69 resizes typed into lost its first key that way, the key written 1 ms before the answer. On macOS and Linux a program's own request delays no key. |
| Headless mirror | Parses every byte the shell writes into an `@xterm/headless` terminal with 1,000 lines of scrollback, answers the shell's status, attribute and cursor-position queries whether or not a window is attached, since every pane leaves them to it, and snapshots the screen for a pane that attaches. |
| Resize wake-up | On Windows, Git Bash in the pseudo console skips its redraw after some resizes at its prompt, and takes the resize only with its next key, which it drops: the pseudo console sends its cursor-position request after every resize, and once the answer comes, the output stops at the cursor move, with no redraw of the prompt. On a Windows test machine, after 8 of 36 answered resizes, and a command typed after one lost its first letter (`echo` ran as `cho`), with or without the cursor inherited and with a short or a long prompt. So when the output after a resize, or after an attach's redraw, is that and nothing else, the next key from the person or an agent goes in behind one Ctrl+G, which bash drops in its place, and at which readline rings the bell at an empty prompt and keeps a partly typed line; the prompt keeps its old wrap until that key, and no timer runs. During a reverse search (Ctrl+R) the Ctrl+G ends the search and puts back the line from before it, since readline ends a search at any key that isn't a search key, so no key would leave it alone. A redraw, a key before the output stops there, or a command running sends none, and neither does another shell or another platform. The shells already run on the ConPTY that comes with node-pty (conpty.dll with OpenConsole.exe, 1.25.260303002), as Noldova Desktop starts every pseudo-terminal with `useConptyDll`, and the probe above ran on it, so the newer ConPTY doesn't end the stall. That Git Bash's MSYS2 runtime takes the new size only as it next reads input is a guess, not yet checked against its source. |
| Resize lead-in | On Windows, Git Bash, and any bash in the pseudo console, which on Windows is an MSYS bash, can lose the first key that reaches it after it has taken a resize, whatever the prompt or program: with a plain `cat` in Git Bash and no Noldova code, about 1 run in 7 of eight resizes each lost one key, always the first after a resize, at 100 or 400 ms after it, and none was lost without resizes; a key that arrives with the resize is kept. The MSYS2 runtime's console thread reads every input record and writes back all but the resize and signal keys, so a key that arrives as it handles the resize can be lost. So after a resize, the next input the session writes, a key or a held key, is preceded by a no-op Shift press and release (`ESC[16;42;0;1;16;1_ESC[16;42;0;0;0;1_`, win32-input-mode, which the pseudo console reads as a key event with no character and the runtime skips), and that input and any after it wait 50 ms before they go; a resize during the wait leads the held keys in again, a cursor request open at its end keeps them until its answer, and the shell's exit drops them. On a Windows test machine that kept every key in 40 of 40 runs, and a Shift press sent with the resize instead, with no wait, still lost one in 3 of 20. No output of the shell shows when it can take keys again: holding the resize until the shell echoed the keys before it still lost one in 6 of 24. Only bash on Windows waits, once per resize and only when a key follows; other shells and other platforms get every key at once. VS Code holds Git Bash's first resize for a second for a like reason (`terminalProcess.ts`, `DelayedResizer`). |
| Escape-sequence tracker | Keeps the unfinished escape sequence at the end of the output, which a snapshot cannot hold, and sends it with the snapshot so the pane's parser starts where the mirror's is. |
| Output batches | Sends output every 16 ms or at 65,536 UTF-16 code units, each batch numbered by its offset in UTF-16 code units since the shell started. |
| Stored lines | Keeps each line that leaves the mirror's scrollback in the terminal's files, so a pane pages it back in ([Stored lines](#stored-lines)). |
| Flow control | Pauses the shell while the mirror or a visible pane is more than 1,048,576 behind, and resumes it at 262,144. What the mirror has still to parse and what a pane has still to acknowledge count in UTF-16 code units, and the mirror's stored lines still to be written count in UTF-8 bytes of their JSON. A pane that holds the shell back for 10 seconds is detached and told so: one more than 1,048,576 behind, or, while the shell is paused, one more than 262,144 behind, which keeps it from resuming. Panes stay counted while the shell is ended, so a restarted shell waits for them at once. |

### Stored lines

- Each line that leaves the mirror's 1,000 lines of scrollback is stored as its text, whether the next line continues it, and its runs of color and style, one JSON line each.
  A resize grows the scrollback while xterm reflows, then stores the lines beyond it in order, so none is lost or stored twice.
  Nothing of the alternate screen is stored.
- `terminal.open`'s `storedLimit` caps a terminal's files, from 10 MiB to 10,000 MiB; the window sends the Output kept per terminal setting, `terminal.outputLimit`, 100 MiB by default.
  The lines go to two files that share the limit: when the newer one fills its half, the older one is dropped and its file reused, and the dropped lines are counted.
- Output and attachments give the stored range: its first and end line, numbered from the terminal's start, and how many lines were dropped.
  `terminal.lines` reads a page in that range, and a page always matches the range it gives, as lines are dropped during the read.
- After a write or a removal fails, the terminal stores nothing more and a read says its stored lines could not be written; a file that ends early reads as damaged.
- Erasing the saved lines of the normal screen (`CSI 3 J` or `CSI ? 3 J`) or a full reset (`ESC c`) clears the stored lines; the numbering goes on.
- The files are private to the person, in one private folder for the runtime, `noldova-terminal-lines-<process id>-<six characters>` in the system's temporary folder, made at the first open.
  Before it holds a terminal's files, the runtime makes it private as it does the shell integration's folder: on Windows icacls removes what it inherits and grants only its owner, SYSTEM and the Administrators, and on macOS `chmod -N` removes its ACL.
  When that fails, the runtime logs why and removes the folder, and the terminal opens without stored lines: a read says they could not be written.
  Only a folder that can't be made at all fails the open; either way, the next open tries again.
  That open first removes the folders whose runtime no longer runs, and never another running runtime's.
  A crashed runtime's folder goes at the next start, unless another process has taken its process id by then: the folder then stays until a later start finds that id free.
  A runtime in another process namespace that shares the temporary folder, such as one in a Linux container, can't see this runtime's process, so it would remove this runtime's folder.
  Closing or forgetting a terminal removes its files, and ending the terminals removes the folder once every terminal has closed its files.
  The folder moves to the part's own data folder once Noldova Desktop gives it one.
- A pane pages the stored lines in through its `TerminalPager`.
  Scrolled to the top of its scrollback, it attaches again for a new screen, reads the lines stored since its last one, then the 500 above them, and draws them above that screen, keeping the line that was at the top in place.
  The connection holds the output that arrives while the pane draws, and writes only what follows the new screen, so no line is lost or doubled.
  Typing and resizes still reach the shell meanwhile, and an attach that comes meanwhile, as when the runtime starts again, draws its screen after this one.
  Above the first stored line, it says in dim italics how many older lines were dropped.
- A pane keeps up to 50,000 stored lines, 100 such pages, each drawn above the live screen, which stays attached and takes typing and output as before.
  The cap is for memory: xterm keeps 3 32-bit numbers per cell, about 1.4 KB for a line of 120 columns, so 50,000 lines take about 70 MB in the window, and each page up redraws every line the pane holds, about 0.7 seconds at 50,000 lines on a developer's PC.
  While pages are loaded, xterm's scrollback is its 10,000 rows plus the rows their lines take at the pane's columns, each at least one, counting a character from U+1100 or outside the Basic Multilingual Plane as two cells, which may count more than xterm draws but never fewer, so a line stored wider than the pane, which wraps to more rows, never pushes the top out and output under the pages has as much room as without them; it is 10,000 again once the pane shows a new screen alone.
  One more page leaves its live screen behind: it draws only its pages, still acknowledges the output it doesn't draw, and pages down as the person scrolls to the bottom, until the newest page meets a new screen.
  Typing there brings the live screen back at the bottom.
- A page that can't be read is logged; a pane that was attaching shows its new screen alone, and one that left its screen behind keeps its pages.

### Starting a shell

- Each shell and one-shot command starts from the environment as it reads when it starts, without the host process's own variables, such as `ELECTRON_RUN_AS_NODE`, and with `TERM` and `COLORTERM` set.
  - On Windows that is the inherited environment with the machine's and then the person's variables laid over it, read with the system folder's `reg.exe`.
    Each read runs `reg export` for `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Environment` and then `HKCU\Environment`, each into its own file, and removes both files once read. The two exports run one after the other, so two reg.exe never write at once. When an export exits with an error, `reg query` for the key tells a missing key from a failed export by its exit status alone, since reg.exe's messages come in the system's language. A key it finds was there and its file failed, as reg.exe's "Unable to write to the file" did now and then on the hosted Windows runners (#12). Then it logs that and exports the key once more, 250 milliseconds later, into a file of a new name. A person's key it doesn't find holds no variables; any other failure counts at once. No process stays running: an export takes about 50 milliseconds, where a Windows PowerShell kept for the reads took up to 22 seconds to start on a Windows on Arm runner.
    The export is UTF-16, so non-ASCII names and values arrive whole, which `reg query`'s console code page would lose. It holds each plain value as quoted text and each `REG_EXPAND_SZ` one as its bytes, unexpanded; other kinds and the default value are left out.
    The runtime builds the variables as Windows does for a new process: each scope's plain values, then its expandable ones, expanded against what is set so far, so a value can name a variable set after the app started.
    Names match without regard to case, `Path` joins the machine's with the person's, and a variable deleted since the app started stays until it restarts.
    The files go into one folder, `noldova-terminal-environment-<six characters>` in the system's temporary folder, made at the first read, made again before a read that finds it gone, as after a temporary-file cleaner, so `reg.exe` never fails for want of it, and private to the person as the shell integration's folder is, since the variables can hold secrets; a folder that can't be made private is removed and nothing is exported. The runtime removes it when it ends, and again once an export under way then settles, since Windows refuses to remove a file `reg.exe` still holds; a read under way makes no folder after the end.
    The runtime reads once when it starts; a shell that opens before that read ends waits for it, and shells that open together share one read. Each later shell reads again.
    A person's key that `reg export` refuses, exiting with an error, and `reg query` doesn't find, as for a missing `HKCU\Environment`, counts as holding no variables, and nothing is logged: `reg.exe` says why only in the system's language. An export that doesn't start, doesn't finish within 5 seconds or can't be read starts the waiting shells with the inherited environment, and the module's log says why: when `reg.exe` doesn't start, doesn't finish or exits with an error, the log names the key, and for an error adds the last 1,000 characters `reg.exe` wrote to its errors, on one line; the next shell reads again.
    An export holds the key's subkeys after its own values; only the key's own values count.
  - On macOS and Linux it is the inherited environment; the shell's own startup files do the rest.
    On macOS, when none of `LANG`, `LC_ALL` and `LC_CTYPE` is set to a value, as for an app started from the Dock or Finder, the runtime reads the person's region setting once at its start with `defaults read -g AppleLocale`, without waiting for it; a shell that opens before it answers waits at most 2 seconds.
    `LANG` is then set to UTF-8 in that language and region, such as `fr_FR.UTF-8`, when macOS has that locale in `/usr/share/locale`, and `LC_CTYPE` to `UTF-8` otherwise, as for a language without a region.
    When `defaults` fails, answers no locale, or takes longer, the runtime's own locale stands in, which is `en-US` when no locale variable is set; a locale that is set stays as it is.
    The runtime stops `defaults` only when it gives up while `defaults` has neither answered nor ended, at the time limit or the part's end: by the time its line is read it has already ended, and stopping its process group before Node reaps it makes macOS answer EPERM, which Noldova Desktop logs as a failure.
- On Linux, before the first PowerShell of each runtime folder starts, the runtime makes `$XDG_RUNTIME_DIR/.dotnet/shm`, with `.dotnet` before it, each with mode 0700 when it is missing; a folder that exists keeps its mode and what it holds, and nothing else there changes.
  Each folder is made only inside one that exists, so a runtime folder that is missing stays missing, and a relative `XDG_RUNTIME_DIR` is skipped.
  .NET 10 makes that folder with its first named mutex, through a temporary folder that it renames into place, and the rename replaces a folder another process has just made.
  PSReadLine takes a named mutex for its history file as each pwsh starts, so when several pwsh start at once with no folder yet, one of them can fail to start its line editor, with `System.IO.IOException` naming `PSReadLineHistoryFile_…` at its prompt.
  The runtime folder, `/run/user/<uid>`, is empty after each boot, so a person who gets several pwsh terminals back at once after a reboot, or an app that opens several together, can hit it.
  This is .NET's bug, dotnet/runtime#136236.
  When the folder can't be made, PowerShell starts anyway and the module's log says why, once for that folder.
  The step goes once the PowerShell 7 releases people run are built on a .NET 10 with its fix, dotnet/runtime#136541, or on .NET 11, which doesn't have the bug.
- On Windows the shell list offers PowerShell 7, Windows PowerShell, Command Prompt and Git Bash, the first one found by default, then each WSL distribution but Docker Desktop's, the default distribution first, then each Visual Studio installation's Developer Command Prompt and Developer PowerShell.
  - PowerShell 7 is looked for in `%ProgramFiles%\PowerShell\7`, then in the `PATH` folders, then in `%LOCALAPPDATA%\Microsoft\WindowsApps`, where a Store install keeps its app execution alias.
  - Git Bash is looked for in the `Git` folder of `%ProgramFiles%` and `%ProgramFiles(x86)%`, in `%LOCALAPPDATA%\Programs\Git`, where a per-user install goes, and beside each `PATH` folder named `cmd` that holds `git.exe`.
  - It looks only in absolute `PATH` folders, so a relative entry such as `.` can't supply a planted `pwsh.exe`.
  - A program counts when it is a file, or a link that `stat` may not open, as an app execution alias is: Windows starts the alias, though `stat` is refused on it with `EACCES`. A link to nothing, a link loop and a folder don't count, so none of them becomes the default shell.
  - The WSL distributions come from the person's `Lxss` registry key, which a one-time Windows PowerShell reads, since `reg.exe` loses non-ASCII text; each opens as `wsl.exe -d <name>`, and its id is `wsl-<name>`.
    Distributions whose names start with `docker-desktop` run Docker Desktop's engine, not a shell for the person, so the list leaves them out.
  - The Visual Studio installations come from `vswhere.exe` in `%ProgramFiles(x86)%\Microsoft Visual Studio\Installer`, which the Visual Studio Installer puts there.
    An installation's Developer Command Prompt is the Command Prompt found with `/k <installation>\Common7\Tools\VsDevCmd.bat -startdir=none -arch=<arch> -host_arch=<arch>`, offered when the script exists.
    Its Developer PowerShell is PowerShell 7, or Windows PowerShell without it, which imports `Microsoft.VisualStudio.DevShell.dll` beside the script and enters the developer shell with `Enter-VsDevShell` after the person's profiles and before the shell integration's script, in the same encoded command; it is offered when the module exists.
    Their ids are `vs-<instanceId>-cmd` and `vs-<instanceId>-powershell`, and `<arch>` is the runtime's architecture as VsDevCmd names it: `amd64`, `x86` or `arm64`.
  - Each list is read once, when a shell list or a shell that isn't installed is first asked for, through the part's context with a limit of 60 seconds, since Windows PowerShell can take 20 seconds to start.
    Opening an installed shell, or the default shell, never waits for the lists.
    A list that fails to read is left out, the module's log says why, and the next request reads it again.
- On macOS and Linux it takes the person's login shell from the user database, or `$SHELL` without one, even when `/etc/shells` doesn't list it, since the person chose that shell; the listed shells follow it, except programs that aren't shells to open a terminal in: `tmux`, `screen`, `git-shell`, `nologin` and `false`.
  Each starts as a login shell, with `-l`, so it reads the person's login profile, such as what it adds to `PATH`.
- Each shell `terminal.shells` lists carries its kind, which a window shows as the icon of the shell's tabs: PowerShell for PowerShell 7, Windows PowerShell and a Developer PowerShell, CommandPrompt for Command Prompt and a Developer Command Prompt, Bash for Git Bash and Wsl for a WSL distribution; on macOS and Linux Bash, Zsh, Fish and PowerShell for `bash`, `zsh`, `fish` and `pwsh`, by the file's name, and Other for any other shell.

### Shell integration

Bash, zsh and PowerShell run a script after the person's startup files that marks each prompt, command, exit code and working folder with `ESC ] 6973 ; kind ; nonce [; value] BEL`; other shells start without it.
Right after it reads its nonce, before the person's startup files and the terminal's note, each script sends a loaded mark, `L`, so the runtime knows the integration runs and waits for the first prompt while the startup files run, up to 60 seconds after the mark; the loaded mark counts as no prompt or command mark.
Each prompt also reports PATH, as `P` with `Path=`, before its working folder, at the first prompt and then only when PATH changed, as after activating a virtual environment; Git Bash converts it to Windows' form with its own `cygpath -w -p`.
Git Bash also reports its `/tmp` in Windows' form, as `P` with `Temp=`, once at the first prompt, by `cygpath -w /tmp`: msys mounts `/tmp` from the TEMP of the first msys program still running, such as the Git Bash that started the app, so it can be another folder than the shell's own TEMP.
When `cygpath` fails or prints nothing, Git Bash sends no `Temp=`, and the runtime reads `/tmp` as the folder the TEMP the shell started with names, without a log, as it does for a PATH it can't convert. It keeps that TEMP from the shell's start, and a restart's, so a later read of the Windows environment doesn't change it, nor one that fails and gives the app's own environment, whose TEMP can be another folder.
When a shell can't send its PATH, because cygpath fails or the escaped value is longer than 19,456 characters, it sends `P` with `Path` and no value instead, and completion goes back to the start PATH; bash and zsh count bytes, which are never fewer than the runtime's UTF-16 units.
Bash and zsh also report their aliases, functions, builtins and keywords, apart by spaces, as `P` with `Names=`, after PATH, at the first prompt and then only when they changed, for `terminal.findCommands`; a list whose escaped value is longer than 19,456 characters sends `P` with `Names` and no value, and the runtime then finds no command missing, as it does before a shell's first list; for PowerShell the module's log says which, once until that changes.
bash 5.3 lists them with `compgen -V` into a variable at each prompt; an older bash lists them with `compgen` in a subshell, which takes a few milliseconds on Linux but over 50 in Git Bash, so an older Git Bash sends no names and shows no command as missing. zsh reads its `aliases`, `functions`, `builtins` and `reswords` parameters.
Both also report their builtins and keywords apart, as `P` with `Builtins=`, for completion alone: bash once, at the first prompt, with `compgen` in one subshell, which an older Git Bash takes too, as it costs ~50 ms only once; zsh at the first prompt and whenever a module changed them. So a Git Bash that sends no names still completes `cd` or `export`, and a names list too long to send, whose reset drops the aliases and functions, never takes the builtins and keywords with it; a builtins list over the same 19,456 characters sends `P` with `Builtins` and no value.
PowerShell reports its functions, aliases and loaded modules' commands the same way, in about a millisecond at each prompt, and its `PSModulePath` as `P` with `ModulePath=`, after PATH, at the first prompt and then only when it changed; a value too long for the mark sends `ModulePath` alone, and the start `PSModulePath` stands in.
Each zsh and PowerShell prompt also reports, as `P` with `Options=1` or `Options=0`, whether the shell's hidden completion binding is in place, at the first prompt where it is and then only when that changed; the binding answers with an options mark, `O`, whose fields are each escaped apart, so an escaped `;` stays inside its option ([Completion list](#completion-list)).
Functions starting with `_`, as bash-completion's and compinit's hundreds of helpers, are left out, so the list stays under the limit, and the runtime never shows a name starting with `_` as missing.
A shell checks a value's length before escaping it, since escaping never shortens it, and skips the byte walk for a value with nothing to escape; the escaped value goes into a variable, with no subshell.
The hooks run with xtrace off, so `set -x` doesn't print the lists at each prompt, and turn it back on as they end; the copies of PATH and the names they keep are never exported, even under `set -a`.
The scanner drops any mark longer than 20 KiB, from its introducer to its terminator, whether it arrives whole or split across reads.
A value escapes the C0 controls, `;`, `\`, DEL and the C1 controls, U+0080 to U+009F, as `\xHH`, which the scanner decodes; bash and zsh walk the value's bytes, so a C1 control is UTF-8's `C2 80` to `C2 9F` there.
The scanner ignores the C0 controls and DEL that arrive inside a mark, as a terminal does: bash 3.2's readline breaks the row of a prompt wider than the terminal inside the prompt's end mark, with CR LF CR in its nonce.

- Each new working folder a prompt reports goes to windows as `terminal.cwdChanged`, and `terminal.attach` gives the last one, or null before the first and for a shell without integration; a blank folder, or one over 4,096 characters, isn't sent and leaves the last one.
- Each shell gets its own random nonce, and the runtime takes only marks that carry it.
  The nonce stops a program's output from forging marks, but not a script the person sources into the shell itself, which can read it from the shell.
- The nonce reaches the shell in a file of its own, never in the shell's environment, whose starting copy stays readable to the shell's programs after the shell unsets a variable: in `/proc/<pid>/environ` on Linux, and in the process's environment block on Windows, where Git Bash's unset leaves the block as it was and PowerShell's leaves the removed variable's bytes past the block's end.
  macOS shows no other process's environment of Apple's own `/bin/bash` and `/bin/zsh`, but does of other programs, such as a Homebrew shell.
  - The file lies in the integration's folder under a random name, `nonce-` and 32 hex digits, and holds only the nonce; the shell's environment holds the file's path in `NOLDOVA_TERMINAL_NONCE_FILE`.
  - The folder is made with mode 0700 and the file with 0600, and the folder is made private before it holds anything: a folder takes the entries its parent passes on, and a temporary folder can pass on a group's read, such as one another program adds.
    - On Windows the runtime runs `%SystemRoot%\System32\icacls.exe` through the context's programs, which removes what the folder inherits and grants full control, inherited by all it holds, to its owner (OWNER RIGHTS, `S-1-3-4`), SYSTEM and the Administrators group, which can read every file anyway.
    - On macOS an inherited ACL entry that allows beats the mode, so the runtime runs `/bin/chmod -N` the same way, which removes the folder's ACL; what it holds then inherits none.
    - On Linux the mode is enough: a new folder's 0700, and the file's 0600, mask every entry a parent's default ACL gives it.
    - When the program fails or, on Windows, `SystemRoot` isn't set, the runtime removes the folder if it can, writes why to the log, and shells start without the integration until a later shell's folder is made private.
  - The script reads the file, empties it and removes it before the person's startup files and before a developer PowerShell's start command, and unsets the variable.
    bash's system-wide startup file, `/etc/bash.bashrc` on Debian, Ubuntu and Git Bash, runs before its `--init-file`, and zsh's system-wide `/etc/zshenv` runs before the module's `.zshenv`, so a program those start can still find the file while it lies there.
    PowerShell starts with `-NoProfile`, and its encoded command runs the person's profiles once the file is read, as PowerShell's host runs them: each one that exists, in the host's order (all users' for all hosts, then for this host, then the current user's), dot-sourced at the global scope under the execution policy, with a profile's error written and the next profile run.
    PowerShell's own line saying the profiles took over 500 ms to load no longer shows.
    The PowerShell integration's own steps, reading the folder and path marks and binding its PSReadLine key, end in an empty `catch`, since a profile or module that makes them fail must not break the person's prompt; the shell then runs without that mark or key.
    No variable the scripts keep that holds the nonce is exported, even where the person's startup files turn `allexport` on.
    bash, with `promptvars` on as it is by default, writes the marks into PS1 and PS0 by their variables' names, so an exported PS1 or PS0, as a virtual environment's activate script exports PS1, holds no nonce.
    zsh's PS1, and bash's when its marks went in with `promptvars` off, hold the marks and are unexported at each prompt, so a line that exports PS1 and starts a program at once still hands the nonce to that program. Either form of bash's marks counts as marked, so a later change of `promptvars` doesn't add them twice.
  - The runtime removes the file too once the shell's output carries the nonce, at the shell's exit, as for a shell that ends before its first mark, and when the shell fails to start; the folder goes when the part deactivates.
  - A file that can't be written starts that shell without integration, and the module's log says why; one that can't be removed is logged.
- Bash starts with `--init-file <script> -i` in place of its listed arguments.
  When those asked for a login shell, the script reads the profile files a login shell reads, but bash itself is not a login shell, so `~/.bash_logout` doesn't run.
- Bash 4.4 and later mark a command's start from `PS0`, which bash expands for every command line it runs, one that starts with a subshell such as `(exit 3)` included.
  Older bash, such as macOS's own bash 3.2, or a bash with `promptvars` off, marks it from a `DEBUG` trap when the person has none, and bash runs no `DEBUG` trap for a line that starts with a subshell, so that line gets no command start mark.
  With `promptvars` on, its end still comes: the prompt's hook leaves the end mark with the line's status when no trap fired since the last prompt, and `PS1` sends it before the prompt's start only when the shell's command number, `\#`, which grows only when a line runs, grew since the last prompt, so an empty line ends nothing.
  With `promptvars` off such a line gets no end mark either; the next prompt still comes, and an agent's command, like a launch's, ends at it without an exit code or working folder.
- Zsh reads the scripts through `ZDOTDIR`, and they read the person's own `ZDOTDIR` files; PowerShell gets `-NoProfile` and the script as an encoded command after its arguments.
- When the scripts can't be written, shells start without integration and the module's log says why.
- When the part deactivates, the scripts are removed after every shell has ended; if they can't be, the module's log says why and the part still deactivates.
- A mark starts at `ESC ] 6973 ;` or at its 8-bit form, `U+009D 6973 ;`, as the escape-sequence tracker reads either introducer as an operating system command's start; the scripts write the first. Both read the decoded text, so a 9D byte inside a UTF-8 character never starts a mark. Inside a mark, U+009D is part of it, since the tracker doesn't end an operating system command there.
  The tracker reads U+009D as an introducer only outside another sequence. Inside an operating system command other than a mark, such as a title, or inside a DCS, SOS, PM or APC string, it's content. Right after ESC, after ESC and an intermediate such as `ESC (`, or inside a control sequence, it ends that sequence. The scanner follows no sequence but its marks, so it starts a mark in each of these; such a mark comes from a program, never the shell, so it lacks the nonce and is dropped. `ESC ]` reads the same in both, since an escape ends or restarts any sequence in the tracker.
- A mark ends at its BEL or ST, as `ESC \` or the 8-bit U+009C. The scanner ends the sequence unfinished at CAN, SUB or any other escape inside it, such as another introducer, where the escape-sequence tracker also ends an operating system command, so a program that prints an unterminated `ESC ] 6973 ;` doesn't take the shell's next mark with it. An unfinished sequence over the maximum is dropped but for an escape at its end, which may start the shell's next mark.

### Ending a shell

Every terminal ends once, however often it is asked to: when it closes, and when the part deactivates or the runtime stops.
An open still under way when the part deactivates is refused at its next step and starts no shell, and a shell that started just then is ended at once.
Every shell and one-shot command starts through the part's context, in a pseudo-terminal Noldova Desktop owns, as the Windows PowerShell and `defaults` that read the environment start through it over pipes (`src/noldova.terminal/src/services/line-process.ts`).
Noldova Desktop records each program, ends it with the part, also when its activation or deactivation fails, and when the runtime stops, also for an update, and ends what a crashed runtime left; the runtime part runs no program of its own and lists no processes.

- A shell with integration that has left its prompt, in a command or in its prompt hooks, gets up to 500 ms to draw its next prompt before it is ended. Bash hangs up its jobs when it is hung up, but not while its prompt hooks run, so a background job such as `sleep 600 &` would otherwise outlive a terminal closed just after the command. A shell at its prompt that was entered a line counts as having left it until it draws its next prompt: readline has handed the line over before the command's mark comes, and a hangup bash takes then is only noted, so bash would wait at its next prompt until the kill. A line entered while the shell wasn't waiting at its prompt, as while it started or ran a command, or a second line before the first's command started, is typed ahead: readline takes it at the next prompt, so that prompt counts as entered too; a command that read the line itself only makes a close at that prompt wait the 500 ms. The line breaks of a bracketed paste put the lines on the line and enter none, and one entered into a continuation prompt such as `PS2`, which has no marks, makes a close wait the 500 ms and then hangs up the shell, which readline is reading for. A shell waiting at its prompt, with no line entered since it drew it, or without integration, is ended at once. The wait is capped, so a prompt whose hooks take longer than 500 ms can still leave such a job running, and a shell that never draws its prompt again, as after `exec sleep 600`, is hung up after the 500 ms and, if the hangup doesn't end it, killed 3 seconds later, as below. Ending every terminal, as the part does when it deactivates, waits for them together, so at most 500 ms in all.
- The shell then ends through its pseudo-terminal's stop, which belongs to Noldova Desktop. It resumes the shell's output; on Windows it closes the pseudo console, and on macOS and Linux it hangs up the shell's process group; whatever still runs 3 seconds later is killed. Bash only notes a hangup that comes after a command and before readline sets its signal handlers for the next prompt, and then waits at that prompt, so such a bash is killed after the 3 seconds. Once the prompt shows, readline catches a hangup and checks for one before each wait for input, so only a hangup between that check and the wait is still missed; the e2e therefore ends bash once its next prompt shows, which narrows the window rather than closing it. Once the program exits, Noldova Desktop closes its pseudo console on Windows and stops node-pty's output worker.
- On macOS and Linux it then hangs up the process groups of the shell's jobs that still run, which it lists before the hangup without starting a program, from `/proc` on Linux and through its own addon on macOS, so the jobs end even when bash lost its hangup between a command and its next prompt. It signals only a group in which a listed process still runs with the same start. A job that ignores the hangup, as `nohup` makes it, keeps running; a job bash was told not to hang up with `disown -h` is hung up too; a job that left the terminal's session, as `setsid` makes it, is found only while the shell is its parent.
- A shell whose stop had to kill it or one of its jobs is written to the module's log. A shell Noldova Desktop ends itself as it stops, also for an update, before the module's end reaches it isn't written there, even when Noldova Desktop killed it: the module's stop then finds it ended.
- Noldova Desktop starts no program once it begins to stop or to prepare for an update, so a terminal opened or a one-shot command asked then fails to start.
- node-pty on macOS and Linux reports a shell's exit only once the shell's output closes, and never if that close doesn't come. Noldova Desktop then reports the exit once it finds the shell's process gone and node-pty has reported none for a second, without a code or signal, and Terminal publishes it as any other.

### Restarting a shell

`terminal.restart` starts the same shell again in the same terminal and folder, at the size of the pane that asks, so a pane and a tab keep their terminal.
- A running shell ends first, as a close ends it, but its exit isn't sent as `terminal.exited`, since the terminal goes on: a pane goes from running to running again, and a launch doesn't end. A restart that fails to start the new shell sends the old shell's exit then, and a launched terminal that closes during a restart sends its `Close` end once. A shell that hasn't reported its exit once its stop in [Ending a shell](#ending-a-shell) ends is written to the log as left running and sends no exit, and its late exit is ignored. The new one starts from the environment as it reads now, with a new integration nonce, and agents' commands are tracked afresh.
- The terminal's output goes on at the next offset with a reset the runtime sends first: it leaves the alternate screen, soft-resets the terminal, turns mouse reporting and bracketed paste off and scrolls the old screen up into the scrollback by the asking pane's rows. The mirror and every pane draw it alike, so the old output stays above the new shell, and a pane keeps all it drew.
- An ended pane keeps fitting its screen to its box, and asks for a restart at the size it has then. A taller pane on the same terminal keeps the top of the old screen in view until the new output scrolls it up. After a shell failed to start, the panel has no pane to measure and restarts at the opening size, which the pane fits once it attaches.
- A new shell starts paused while a pane is still more than 1,048,576 UTF-16 code units behind.
- A restart asked while another is under way waits for it, then runs; one whose terminal closed meanwhile starts no shell, or ends the one it started.
- An agent's terminal isn't restarted, since its agent session starts and ends its shell: the runtime refuses it, and neither its tab's strip nor its tab menu offers Restart.
- An ended terminal takes no input until it restarts: the runtime drops it, and the pane takes no typing.

### Terminals across runs

The runtime keeps the person's terminals that the app's connection opens, but an app's launched ones, in the module's database, whose migration `create-terminals` makes their table and `add-terminal-owner` adds each terminal's owner; an agent's terminal isn't kept, since its agent session starts and ends it.
- Each row holds the terminal's session id, its shell, its last folder, whether it is a window's panel terminal, its owner, the person's name for it, which the migration `add-terminal-name` adds, and its place in the order the terminals opened. Opening a terminal adds its row, the working folder the shell's integration reports replaces the folder, and closing a terminal, or forgetting an ended one, removes the row; ending the runtime keeps every row.
- `terminal.restore`, which a window's part asks at activation and when the runtime started again while the window stayed, opens each kept terminal again once a run, at the size it gives and keeping the output it gives, the Output kept per terminal setting's, with the same session id, so a saved tab keeps its place and an open pane attaches to it: the same shell in the last folder. The shells start together, and the terminals are listed in the order they were kept. A panel open that comes during a restore waits for it, so it gets the panel terminal the restore brings back. A shell no longer found starts the shell the request gives, the Default shell setting's, while the runtime finds it, else the runtime's default, and a folder that no longer exists or isn't absolute opens the home folder; the module's log and the terminal's first line say so, on one line. Only the latest panel terminal opens again, and the others' rows go.
- A terminal whose shell can't start again is written to the log and its row removed; the others still open. Rows that can't be read are written to the log and open nothing, and a row that can't be written is written to the log while its terminal opens and runs.
- The earlier output isn't kept: a restored terminal starts with a new shell and empty stored lines.

### Terminals an app launches

An app's window part launches a terminal through the published `TerminalLauncher`, which sends `terminal.launch` through the app's own context and opens the tab through the terminal part's, since a part opens only its own module's views; a launch without a tab, for a terminal the app shows only in its own page through `EmbeddedTerminal`, opens none, and the runtime lists it without one, so a window opening again doesn't give it one either, and ends it when the window that launched it closes for good or reloads, since no other window shows it ([INTEGRATION.md, Terminals the app launches](INTEGRATION.md#terminals-the-app-launches)).
- The protocol and the window check the variables before anything opens: portable names, none the terminal sets itself (`TERM`, `COLORTERM`, `ZDOTDIR` and the `NOLDOVA_TERMINAL_` names), in any case, and no two names that differ only in case.
  Their names and values hold at most 131,072 characters in all, so a launch past what a program's start takes on macOS and Linux is refused rather than failing as its shell starts.
  A refusal names the variable, never its value.
- The runtime lays the variables over the environment the shell starts from before the shell integration reads it, so the integration's own variables lie over both; on Windows a variable first removes the one whose name matches in any case.
- The values never reach a log, the module's database or a restore: the terminal isn't kept for the next run, and the runtime holds them on the terminal only while it is open, so that `terminal.restart` lays them over the new shell's environment again.
  Noldova Desktop logs no request's parameters, and none of the terminal's messages holds a value.
- The notice is written as a terminal's note is, one line for each of its lines, above the shell's first output, which starts below it; it never reaches the shell's input.
  On Windows a shell with the integration prints it as its own first output, so it reaches what the shell's output reaches, such as an agent's text and the command tracker; elsewhere, and for a shell without the integration, it is the runtime's own lines.
- The command, when the launch has one, is one line of at most 16,384 characters with no line break, tab or other control character, which the protocol and the window check, so it can't enter itself or send keys of its own.
  The runtime types it and Enter into the shell once the shell is ready: at the first prompt its integration marks, or, for a shell without the integration, once its first output has stopped for 500 ms; a shell whose integration sent its loaded mark is waited for while its startup files run, up to 60 seconds after the mark, the same limit as for a shell that shows nothing, and otherwise it waits at most 10 seconds, then types it anyway. A Run typed at the loaded mark's limit, with no prompt marked, is answered `Typed` and its end comes at once as `NoIntegration`, since no prompt mark came that would mark its command's end; a launch's command typed there ends at once without a code. A shell with the integration that has shown no text after those 10 seconds is still starting, as Windows PowerShell on a busy computer, where its first run of a security command can take 20 to 40 seconds before its first prompt: the runtime waits on until it shows text or its loaded mark, at most 60 seconds from the start. After its first text it waits up to 10 seconds more for the loaded mark or the first prompt, however long the shell rests, and then types, so a shell whose integration never loads still gets the command, and one that shows nothing at all gets it at 60 seconds. The wait ends at once when the shell exits or its terminal closes. The agent tools' wait for a new terminal's first prompt waits the same 60 seconds for a silent shell, and ends at its first text.
  The launch's answer doesn't wait for it, a shell that ended or a terminal that restarted or closed meanwhile gets nothing, even when the old shell outlived its kill, and the wait ends with the terminal or the host, so no timer outlives them; a restart doesn't type it again.
  The shell echoes and runs it as the person's own command, so the tab shows it like a typed one.
  Once the command is typed, the runtime sends `terminal.launchCommandEnded` once, with the sessionId and the exit code of the first command end its integration marks after the typing, so an end mark from before it never counts; an exit code outside what the protocol carries goes as `null`.
  Every integration marks a command's end before the next prompt's start, so a prompt that starts on a new line after the typing without that mark sends `null`: a bash before 4.4 with `promptvars` off doesn't see a subshell such as `(exit 3)`, which then gets no end mark, and the person's next command's end isn't the launch's. A prompt redrawn in place before the shell took the line, as an asynchronous zsh theme does, doesn't count.
  It sends `null` at once when the shell has no integration, or its integration hadn't marked by the typing, as when a startup file runs another shell, or the command wasn't typed, since its end can't be told; also when the person typed into the terminal before the command went in, since the shell may end their line after the typing, though a window's focus reports and its replies to the shell's color queries don't count, and the mirror answers the other queries itself; and on a Restart after the typing; a terminal that ends after the typing and before its command's end sends none, and the window resolves `commandEnded` with `null` at the terminal's end.
  The window listens for it, only for a launch with a command, from before the request, as for the end.
  Only the launching app's own context passes a command: `terminal.launch` reaches the runtime only from a module whose window part Noldova Desktop lets request Terminal's methods.
- A folder that no longer exists is answered rather than replaced with the home folder.
- A launch's shell kinds, when it has any, limit its shell as a run's do: the window sends the Default shell setting's shell with them, and the runtime runs it when it is of the kinds, else its own default when that is, else the first installed shell of them, so a sign-in an app launches reaches the program the person installed on the host even when the Default shell is a WSL distribution.
  With none of them installed, the runtime opens nothing and the launch fails with `ShellKindNotFoundException`; a launch with kinds that fails isn't tried again with the system default, as one without kinds is, since the runtime already falls back to its default within the kinds; a launch without kinds sends no `shellKinds` on the wire and runs the Default shell as before.
- `LaunchedTerminal.closeAsync()` ends a launched terminal as closing its tab does: it closes the tab through the terminal part, which Noldova Desktop doesn't report as the person's close, and sends `terminal.close` through the app's context, so the runtime sends the `Close` end and `ended` resolves `Close`. A terminal that already ended is left as it is, a second close while one is under way is that close, and a close the runtime refuses for a terminal it no longer has, as when the person closed the tab meanwhile, has closed it.
- The window hears of the shell's end from `terminal.exited`, which it listens for from before the request, since the exit can come before the answer, and resolves the launch's `ended` once: `Exit` when the shell exits by itself, or `Close` when the terminal closed. A restart doesn't end the launch, since the tab stays and the restarted shell takes the launch's variables again; only a restart whose new shell fails to start ends it, with the old shell's `Close`.
  A shell that outlives the kill of a closed launched terminal may never exit, so the runtime sends its `Close` end itself, before it removes the stored lines; the shell's own exit after that sends no second end.
  When the runtime starts again, every launch still waiting resolves as `Detach`, since the new runtime opens no launched terminal again.

### The node-pty output worker

On Windows node-pty keeps the thread that reads the console's output alive after the shell ends ([microsoft/node-pty#887](https://github.com/microsoft/node-pty/issues/887)).
Noldova Desktop's pseudo-terminal stops that worker once the program exits, so the module reaches into no node-pty field of its own.

### The Windows exit code

On Windows node-pty reports a shell's exit when the console's output closes, with the exit code its process-exit callback has given by then, and the two arrive apart.
Over 100 PowerShell runs on Windows (x64), the output closed 27 to 120 ms after the callback in 99, and 59 ms before it in one, which then ended without its code.
When node-pty reports the exit without its code, Noldova Desktop's pseudo-terminal reads the code from the program's process, so such a shell, or a one-shot command, still ends with its code; the module reaches into no node-pty field for it.

### Earlier commands

A terminal of bash, zsh or PowerShell with the integration shows the rest of the newest earlier command that starts with what the person typed, in grey after the cursor, as fish and PowerShell's PSReadLine do.

- Only the runtime trusts the marks, so it tells the window where the shell's line is: each `terminal.output` carries `inputs`, offsets into its data where the line starts, at a prompt's end, or ends, at a prompt's or a command's start or its end; a restart ends it too.
  An agent's terminal gets none, so its panes never suggest; neither does a shell without the integration.
- zsh's integration puts a mark of its own at the start of a right prompt, `RPROMPT`, each time zsh draws it, and the runtime passes it on as a `RightPrompt` input; the right prompt's column comes only from that mark, never from the line's text.
- The runtime's mirror keeps the line's start as a marker, so `terminal.attach` gives it as `input`, rows above the cursor's row and a column, with the column of a right prompt marked on that row since, or null outside a prompt or on the alternate screen.
- zsh and PowerShell give the command they run in their command-start mark, as zsh's `preexec` and PSReadLine have it, so neither a right prompt nor anything else on the line comes with it; for bash, or zsh with its history off, the mirror reads the line from its start over the rows it wraps to, cut before a right prompt marked on its start row unless typed text reaches it.
  Either way a command over several lines gives its first line only, trimmed and cut at 4,096 characters.
  A line that starts with white space gives none, the way a person keeps a command out of bash's and zsh's own history.
  The runtime keeps each shell's commands of this run, newest first, without repeats, at most 200, in memory only, so a command, which may hold a secret the person typed, never goes to disk.
- `terminal.attach` gives the shell's commands as `commands`, and each new one goes to every terminal of the same shell a person types in as `terminal.commandAdded`; a pane keeps the ones that arrive while it attaches and adds them after the attachment's.
- The pane reads what was typed from its own screen, between the line's start and the cursor, so the suggestion follows each echo at once and a prompt that redraws itself in place keeps its line.
  Nothing shows at an empty line, on the alternate screen, while text follows right after the cursor or on the rows the line wraps to, as when the shell draws a suggestion of its own, or where no earlier command is longer than what was typed.
  A right prompt the shell marked keeps the suggestion, which is cut before it.
- The rest is an xterm decoration on the cursor's row, one cell per character in the theme's bright black, cut at the row's end.
- Any input the pane sends hides it until the screen shows that input, so → never takes a rest the screen no longer matches: text alone once the line reads as before plus all the text sent since, whatever echoes are still on their way; other input, or text the shell drew otherwise, once the shell wrote after it and then neither input nor output came for 100 ms, or once no input came for a second, for a key the shell doesn't answer.
  This is the guard for keys the shell answers itself, the same for bash, zsh and PowerShell: their echo can't be predicted, as a key bound to a widget or a completion may redraw anything, so like a terminal's typeahead it waits for the shell to go quiet. 100 ms is well past a shell's answer to a key on the same computer, a few milliseconds, and short enough that the rest comes back before the next key a person types; a second ends the wait for a key the shell never answers, such as one bound to nothing, so the rest never stays hidden.
- → or End with no modifier, while the rest shows, sends it to the shell as typed; any other key goes to the shell as before.
- The setting Suggest earlier commands, `terminal.suggestions`, on by default, turns it off in every pane at once.
  Turning it off drops the commands the runtime and each pane kept, at once; while it is off, the runtime keeps no command and sends none.
  The setting is shared, not for one device, because the runtime reads it and has no device of its own.
- The runtime leaves PSReadLine's own predictions as the person's profile sets them.
  A prediction PSReadLine draws inline is text after the cursor, so the rest shows nothing while it is there, and only one suggestion shows.
  PSReadLine's list view draws below the line, so there the rest and the list both show.

### Command colors

A terminal of bash, zsh or PowerShell with the integration can color the command the person types at its prompt, as the shell would read it.

- The pane finds the line as the suggestion does, from the runtime's line start and right prompt marks, and `terminal.attach` gives the shell's kind as `shellKind`, so the pane reads the line by bash and zsh's rules or by PowerShell's.
- bash's and zsh's integrations end the continuation prompt, `PS2`, with a mark of their own each time the shell draws it, as for a command over several lines or a here-document's body, and the runtime passes it on as a `Continuation` input. As with `PS1`, a `PS2` that holds the mark is unexported at each prompt so no program it starts gets the nonce, so a `PS2` the person exported reaches no nested shell, tmux or `sudo -E`, which draw their own default `> `; PowerShell's PSReadLine draws its continuation prompt itself, with no place for a mark, so a PowerShell command is colored on its first line only.
  `terminal.attach` gives no continuation, so a pane that attaches while a command goes on over several lines colors its first line only.
- After each write the pane reads the line from its own screen, from its start over the rows it wraps to, cut before a right prompt marked on its start row, and then each line it goes on to after a continuation mark, joined by line breaks, and splits it into parts: the command's name, a shell keyword, an option, a quoted string, a path, a variable, an operator or redirection, and a comment; a plain argument has no part.
  An interactive zsh reads `#` as a comment only with `INTERACTIVE_COMMENTS`, which it leaves off and the integration doesn't set, so a zsh line has no comment.
  A new command starts after `|`, `&&`, `||`, `;`, `&`, `(`, `$(`, a keyword such as `then` or `do`, a line break unless an escape before it joins the next line, in zsh `&|`, `&!`, `always` and the count after `repeat`, and in PowerShell `{`; `>|` and `<>` are redirections, and the word after a redirection, its target, is never the command, as in `exec >log` or `exec 3>log`.
  A precommand modifier, `builtin`, `command` and `exec`, and in zsh `noglob`, `nocorrect` and `-`, is a keyword, and the word after it and its options, and `exec -a`'s value, is the command's name.
  zsh's own keywords `repeat`, `foreach`, `end` and `always` are keywords, a sole `}` is one anywhere on the line, the words in the parentheses of `for name... (words)` and `foreach name... (words)` run no command, after one loop name or several, and `=name`, which zsh expands to the program's path, is a path.
  A quote still open at the line's end is a string to the end, over the lines it goes on to; a comment ends at its line's end, and a here-document's body, after `<<` or `<<-`, is a string through its delimiter's line.
  Ranges are in the line's UTF-16 units, which the pane maps to cells, so a wide character takes its two cells.
- Each part's cells on a row take an xterm decoration with the part's color, only on cells the shell drew in the default text color, so the colors a shell draws itself, such as PowerShell's, fish's, or the grey of zsh's own suggestion, stay.
- A command's name the shell would find nowhere takes the kit's `--nol-error`, a color only, never an underline.
  The pane asks `terminal.findCommands` about each name typed in plain letters, digits and `._+@%:,-`, once a prompt and at most 64 at a time, one request at a time, and only for bash, zsh and PowerShell; a quoted, escaped or expanded name is never asked about.
  The runtime checks the names against the aliases, functions, builtins and keywords its last prompt reported and the programs on its last PATH, on Windows by `PATHEXT`, for Git Bash a script without an extension too, and in any case; a name with a folder part, `~` or a leading `.` is a path and never missing.
  It answers with none for any other shell, before the shell reported its names, after a names reset, while its PATH is reset, since the start PATH may lack folders it added since, and when a PATH folder doesn't answer by completion's deadline, so a name is never shown as missing on a guess.
  It lists PATH's programs once for each terminal's prompt and PATH, keeping one listing per terminal, so the names typed at one prompt read its folders once, and a program installed meanwhile counts from the next prompt or a restart; a closed terminal's listing goes with its shell.
  A command `hash -p` adds, or an alias defined on the same line that runs it, as `alias x=ls; x`, shows as missing until the next prompt reports it.
  A name keeps the command color until its answer, an answer that comes after the next prompt starts counts for none, and once a request fails the pane asks nothing more until it attaches to its terminal again, as it does after a reconnect.
  For PowerShell, a name its last prompt reported is never missing, nor one that Get- in front of it makes a reported name; the runtime looks each other name up with `Get-Command`, as typed and with `Get-` in front, since PowerShell runs `process` as `Get-Process`, in a PowerShell of the terminal's own program, Windows PowerShell too, started with `-NoProfile` and the shell's PATH, PATHEXT and PSModulePath.
  On Windows, each PSModulePath folder with a `~` in it, as a short 8.3 name such as `C:\PROGRA~1` has, goes to the lookup as its real path, which Windows gives in its long form, since the wildcards below find no command in a module under a folder written with a short name, in pwsh and Windows PowerShell alike; a folder whose real path it can't read, for any system error, or doesn't read within the completion's 1-second read limit, goes as it is.
  `Get-Command` finds a module's commands on PSModulePath before the module loads, so a command PowerShell would load at its first use is never missing; given a name exactly, it imports the module that holds it, which runs the module's code, so the lookup asks only with wildcards, which import nothing: the name with its first character in brackets, which matches only the name, for commands, and the name followed by `*` for programs and scripts, which keep their extension in their name, as `git.exe`, and match no brackets; a program or script counts as the name itself or, for an extension PATHEXT or `.ps1` holds, as the name without it.
  The lookup writes the index of each name it finds nowhere rather than the name, since the console's code page can't carry every name.
  It takes about a second, two in a pwsh that loads its own modules first, as the wildcards look through every module on PSModulePath.
  It answers within 10 seconds and holds neither typing nor the colors, as each name keeps the command color until its answer; one that fails or runs past its time finds none missing, and the module's log says why, with PowerShell's exit code and the last of its errors for a failure, once until a lookup of that shell succeeds (#40).
  A lookup past its 10 seconds keeps running unattended, for at most 60 seconds in all, since PowerShell's first scan of a PSModulePath with many modules can take longer, and PowerShell writes what the scan found to its module analysis cache only about 10 seconds after the scan, while it still runs.
  So a lookup that finishes its scan past the 10 seconds stays 15 seconds more before it exits, and one in time exits at once, and the next lookup reads the cache.
  A shell runs one lookup at a time: until it ends, in time or unattended, that shell's other lookups start none and count every name it hasn't answered yet as found.
  A shell whose PATH or PSModulePath was reset, or without a list of its names, looks nothing up and finds none missing, and the log says which, once until that changes.
  Its answers are kept for each shell until the shell reports other names, PATH or PSModulePath, so a name is looked up once while they stay; a program or module installed meanwhile counts from that change or a restart.
  While PowerShell's PSModulePath is reset, as while PATH is, it finds none missing, since the start PSModulePath may lack folders the shell added since.
  With `autocd`, which zsh and bash from 4.0 report as `*/` among their names, the name of a folder in the shell's working folder is never missing, as it runs `cd` to it; a folder only `cdpath` holds still shows as missing.
  zsh reports each suffix alias as `*.<suffix>`, and a name whose last suffix has one is never missing, as zsh opens the file with the alias's program.
- The colors are the kit's code tokens, in one map in the window's `Resources`: the command `--nol-code-function`, a command not found `--nol-error`, a keyword and an operator `--nol-code-control`, an option `--nol-code-keyword`, a string `--nol-code-string`, a path `--nol-code-type`, a variable `--nol-code-variable`, and a comment `--nol-code-comment`.
  They follow the light and dark themes; in forced colors the kit colors no code, so neither does the pane.
- A line the shell left keeps its colors as it scrolls, and takes new ones when the theme changes.
  A kept part on the screen's rows loses its color once its cells hold other text, as when a program moves the cursor up and writes over them; an erase, as `clear` and Ctrl+L send, drops the markers of the rows it erases, and their colors with them.
  Nothing is colored on the alternate screen, before a line start, or in a terminal without the integration or an agent's, which get no marks.
- The setting Color typed commands, `terminal.commandColors`, off by default, turns it on in every pane at once; off, every color the panes drew goes at once.
  Only the window reads it.

### Completion list

A terminal of bash, zsh or PowerShell shows one list of what can follow at the cursor, the same in every shell.

- `terminal.complete` takes the terminal, the line as the pane reads it from its screen from where the shell's line starts, the cursor in it, and `asksShell` for a key the person pressed to complete.
  It answers with `replaceFrom`, where the cursor's word starts, and at most 500 `items`, each with the `text` the shell gets in place of the line from there to the cursor, the `label` the list shows and its `kind`: `File`, `Folder`, `Command`, `Branch`, `Script` or `Option`, and `isShellTab` when the shell got a plain Tab in place of a list.
  Only a connection that reaches the terminal is answered, as with the other requests; any other shell gets no items.
- `CompletionSource` reads the line up to the cursor into words as the shell does, in `ShellWords`: bash and zsh with quotes and the backslash, PowerShell with quotes and the backtick, a pipe, a semicolon or an ampersand starting the next command.
  It reads no expansion, so a variable stays as typed.
- What it lists:
  - for a command's first word, unless it starts with a dot or `~` or holds a slash, for bash and zsh the builtins and keywords the shell reported apart and the aliases, functions, builtins and keywords its last prompt reported, without its helpers, autocd and suffix aliases, none before its first report, and the builtins and keywords alone after a names reset; for PowerShell a short fixed list of its common cmdlets, since its own commands aren't among the names it reports until their modules load, and asking it for them needs TabExpansion2 in the shell itself, which the Tab the shell answers already does; and every file in the absolute folders of the shell's PATH, on Windows those with a PATHEXT extension, without it;
  - after `git checkout`, `git switch`, `git merge` or `git rebase`, the local and remote branches, from `git -C <folder> for-each-ref` with the git on PATH, within 2 seconds; a folder outside a repository, or a git that fails, gives none;
  - after `npm run` or `npm run-script`, the scripts of the nearest `package.json` up from the folder;
  - else the files and folders of the word's folder, from the shell's working folder; a name starting with a dot shows only for a word starting with one.
    A `~/` starting the word is the home folder only where the shell reads it so: unquoted and unescaped in bash and zsh, and in a quote too in PowerShell.
- The folder is the shell's last reported working folder, else the one it started in.
  Git Bash on Windows reports `/c/Users` for `C:\Users`, which the runtime reads as such, and `/tmp` as the folder the shell reported for it, else the one its TEMP names; any other path of its own, outside a drive, gives no files.
- The environment is the system's from the last read that finished, with a launched terminal's variables over it, with PATH the one the shell reported at its last prompt that did, in place of the start one whatever its case on Windows, so commands a virtual environment adds are listed; before the first report, or for a shell without integration, PATH is the start PATH.
  A completion never waits for a read: it starts one when none is under way and lists from the last finished one, which a shell's start also leaves, or from the app's inherited environment before any finished.
  So a change to the system's variables shows from the first completion after that read finishes. A read that fails, as when `reg.exe` runs too long, leaves the last good one in place for completions, while a shell's start then takes the inherited environment, as [Starting a shell](#starting-a-shell) says.
  On Windows a read's file work waits for one of Node's four I/O threads, which other file work can hold for long, so a completion that waited for it could wait as long (#137).
- Each item's text is written back as the shell reads it.
  In a quote still open at the cursor, it stays in that quote, closed but after a folder, so the person can go on into it.
  Otherwise, as for a word whose quote closed before the cursor, bash's and zsh's special characters are escaped, and a leading `~` that isn't the home folder too; PowerShell quotes it where it must be.
  Where the word binds to the `-Path` of a cmdlet that reads wildcards there, such as `Get-Item`, `cd`, `gc` or `Remove-Item`, a path also escapes its wildcards, `[`, `]`, `*`, `?` and the backtick, with the backtick, and is quoted.
  `PowerShellBinding` binds the words before it as PowerShell does, from each such cmdlet's own parameters (PowerShell 7's, for files), copied into a table since reading them means asking the shell, and the common ones: a `-word` names the parameter whose name or alias it is, such as `-LP` or `-vb`, else the one whose name or an alias it starts, such as `-r` for `-Recurse` on `Remove-Item`, among the cmdlet's own and the common ones first and among the file system provider's dynamic ones, such as `-File` or `-Raw`, only when none of those matches, so `-fi` on `Get-ChildItem` is `-Filter` and `-r` on `Get-Content` is `-ReadCount`; a switch, or a parameter with its value after a `:`, takes no further word, and any other takes the next one. After `--`, every word is positional. Named parameters bind first, then the positional words fill the cmdlet's positions left, in order, so in `Copy-Item -r a e` the `e` is the destination.
  The aliases `ac`, `cat`, `cp`, `ls`, `mv`, `rm` and `rmdir` count only on Windows; elsewhere they name the system's own programs.
  As any other parameter's value, such as `-LiteralPath`'s or `-Destination`'s, after an unknown or ambiguous parameter, which PowerShell refuses, and for a native program, the name is written as it is.
  Where it escapes, the word being completed is read with the escapes taken back, so a second Tab inside a folder named `e[1]` lists it.
  A folder ends with the separator the word used, else `/`, or `\` in PowerShell on Windows.
- Matching is by the start of the word, ignoring case on Windows and in PowerShell; items are sorted by label, without repeats, and an item whose text would be longer than a path, or would hold a C0, DEL or C1 control character, is left out, since the pane types the text as keys and the shell would act on such a character rather than insert it; `TerminalCompletionItem` refuses such a text too, as a command does.
- The runtime keeps nothing between requests: each one reads the folders, PATH and `package.json` again, and runs git again; only a read of the same path still under way for another request is joined, not started again.
- A command's options come from the shell's own completion, the data its Tab reads, with no definitions of the module's own.
  A request with `asksShell`, which the pane sends only for a key the person pressed to complete, never while they type, asks the shell for them when the cursor's word follows a command's name, the shell waits at its integration's prompt, no command runs, and its last prompt that said so reported its hidden binding in place (`Options=1`); else the shell gets no keys at all, since one without the binding would take them as text.
  The runtime sends the binding's keys, PowerShell's PSReadLine chord F12,o and zsh's Ctrl+Alt+F12, and the binding answers with an options mark, `O`, one escaped option in each field after the nonce, at most 500 within the mark's 20 KiB.
  - PowerShell: a PSReadLine key handler reads the line and cursor and runs `TabExpansion2` on them, as Tab does, so a module is imported exactly when Tab would import it; it keeps the parameter names, and for a native program's completer the results starting with `-` that aren't paths. It is bound only where PSReadLine reads the line and no profile bound F12 or a chord starting with it, which the chord would take over; under ConstrainedLanguage, which refuses the call that reads the line, it answers with none.
  - bash: no binding. Bash clears the line from the screen before a `bind -x` command runs and draws it again after, so the line would be blank while a completer runs, which can take longer than the cap; a bash prompt never reports a binding, and a request sends bash no keys.
  - zsh: a zle widget in the emacs and vi keymaps runs a completion widget whose function shadows `compadd` so it records the words a completion function adds, matched against the word, instead of adding them, then sets nothing to insert or list, and keeps those starting with `-`. It is bound only where the person's startup files left Ctrl+Alt+F12 unbound in all three keymaps. A prompt reports it in place only while zle edits the line and compinit is loaded, whenever the person loads it.
  Each binding writes whatever its completers write nowhere, adds nothing to the history and changes neither the line nor the screen, and still answers, with none, when a completer fails or the word is the command's first.
  The shell's options join the list where they start with the cursor's word, as `Option` items whose text is the option as the shell gave it, sorted with the rest, without repeats.
  A shell answers its requests in the order their keys reached it, so the runtime keeps each request's place until its answer comes, a command starts or a new prompt starts: one after a command's end, or after a report the shell sends before each new prompt, as zsh's after Ctrl+C or an empty line, which end no command. A prompt the shell draws again in place, with no end or report before it, as zsh can before it answers, keeps the request waiting: a key the person or an agent types ends every request waiting without options, a pane's reply to the shell, such as a focus report, doesn't, and the answer a request still gets later is dropped, as is an answer no request waits for.
  When no answer comes within 500 milliseconds, or 3.5 seconds until the shell has answered once since it started, the runtime gives the shell a plain Tab and answers with no items and `isShellTab`, so the person gets the shell's own behavior, never nothing; the first answer's limit was set at about 1.6 times the slowest then seen on hosted runners, 2.2 seconds from a loaded Windows PowerShell, where 70 hosted runs on five targets answered within 1.8 seconds. A fresh pwsh on a hosted Windows x64 runner has since taken 4.6 seconds for its first `TabExpansion2` (#161), which that rule would size at about 7.4 seconds. The limit stays at 3.5 seconds: a slower first answer still gets the shell's own Tab, which keeps the promise, while a person who pressed Tab would wait 7.4 seconds for nothing on screen.
- Each request has one deadline, 1 second: a read still going then adds nothing, and no read starts after it, so a folder on a network share that stopped answering leaves the list with what did answer, and a walk up to `package.json` reads such a file once.
  A request while another of the terminal's lists goes on gets its own list; while any of the terminal's lists left a read past its deadline that the system hasn't ended, its next requests get no items, so such a folder holds one of the system's reads.
  The module runs at most two of these reads at once, for every terminal together, and starts the others in the order asked, PATH's order for a command list, as each ends; a read still waiting for its turn at its request's deadline is dropped and never starts, so it holds nothing. Node runs file reads on four threads, so completion's reads, a cold list of 81 PATH folders on the hosted Windows image among them, never take all four: the environment read and a shell's start, which read files too, always have a thread (#139).
- The pane's `CompletionList` asks for the list when the person presses Tab with no modifier at a marked prompt on the normal screen, with `asksShell`, the line up to the cursor and the cursor at its end, and while no input other than text waits for the shell's echo; text on its way counts as typed, as for the [earlier commands](#earlier-commands). Any other Tab goes to the shell.
  - A reply with items opens the list under the cursor's word, from the cell the word starts at, on the row below the cursor, or above it when the list doesn't fit below and there is more room above, kept inside the pane, with at most twelve rows and a scroll bar past them. It stays in the pane, as the terminal's other layers do, so in a pane of a few rows it shows a row or less and scrolls. It is the kit's completion list, `nol-completion-list`, which draws the menu's box and the menu item's rows, each choice's text in the code font (`isCode`) and its kind as the row's muted note, keeps the active row in view and takes the room the pane gives it (`maxHeight`); the pane sets its position, its width and its order over xterm's layers. The focus stays in the terminal, whose input, while the list shows, names the list (`aria-controls`), its active row (`aria-activedescendant`), that it is open (`aria-expanded`) and that it lists completions (`aria-autocomplete="list"`), as the kit's mention field does; the list closes them all.
  - ↑ and ↓ move the active row, wrapping at either end, and Tab, Enter or a click inserts it: the rest of its text when it starts with the word, else, as when the case differs, one DEL a character of the word, then the text; the shell gets it as typed. Escape closes the list and sends nothing.
  - Text and Backspace go to the shell and keep the list, which narrows to the choices that start with the word the screen then shows, ignoring case, keeping the active one when it stays; it closes once none does, or the line no longer starts as it did. Any other key closes it and goes to the shell, as do a blur, a resize, a scroll, the shell leaving its line and another session in the pane.
  - A reply with no items, or a request that fails, which the log says, gives the shell a plain Tab, so the person gets the shell's own completion; a reply with `isShellTab` sends nothing more, since the runtime gave the shell its Tab. A reply that comes after the line changed, or after the list closed for any of the reasons above, is dropped, and a Tab while a request waits does nothing. Any other key that reaches the shell while a request waits ends it, so the next Tab asks for the line it made. A key an input method composes with, such as its committing Enter or its ↑ and ↓ among candidates, stays the method's, with the list open or not.
- The setting Complete with a list, `terminal.completionList`, on by default, turns the list on in every pane at once; off, Tab goes to the shell as typed.

## The window part

The window part is an Angular project in `src/noldova.terminal.window`, with its own exact pins in its manifest, which the root's lockfile records.
It takes Angular and its CDK, pinned exactly among its development dependencies, Noldova Desktop's `@noldova/desktop.window` and its peers, and the kit at the version Noldova Desktop's window workspace holds as peers, which the root manifest pins, and pins the three `@xterm` packages the pane draws with.
Angular's compiler builds with the root's TypeScript, 6.0.3, the one version in the repository.
The part takes `IWindowPart`, its context, the view, document and command contributions and `WindowPartTokens` from `@noldova/desktop.window`, so a host provides its tokens.

- Links: OSC 8 links and plain `http`, `https` and `mailto` URLs, a plain one found across the rows a long line wraps over and placed by the cells its characters take, show their target as the pane's tooltip and open through the window on a left-button Cmd+click on macOS or Ctrl+click elsewhere, with the gesture the kit's `LinkOpenEvent` reads from it, `LinkGesture.Modified`. The setting Open clicked links, `terminal.linkClick`, decides where, and the pane passes that place on every click, whatever the app's Links settings say: by default In your browser, `LinkPlace.System`, since the sign-in links tools print need the person's own browser, where they are signed in, or In the app's browser, `LinkPlace.InApp`; a middle or right button never opens a link, with or without the modifier, since a middle click pastes the selection on Linux; any other scheme never opens. A plain URL counts only within one row.
- Only the runtime's mirror answers a program's status and attribute queries, so the pane swallows them and several panes on one session don't answer twice.

### Terminals with an owner

An app can tie a person's terminal to something of its own, such as a chat: its owner.
A terminal without an owner, a general one, behaves as the sections above say.

- Two classes serve owners, one for each part:
  - `TerminalOwners`, from `@noldova/terminal/window`, is the window part's: an app's window part provides it and closes, shows and runs in an owner's terminals with it.
  - `RuntimeTerminalOwners`, from `@noldova/terminal.protocol`, is the contract of the runtime part's service `terminal.owners`, which an internal class of the runtime part extends, so `./runtime` exports no class of it: an app's runtime part closes an owner's terminals with it and binds agent sessions to an owner, with no window open too.
  - The contract lives in the protocol package, which has no dependencies and only context's packages as peers, so an app's runtime part takes it without the window package and its Angular peers. Noldova Desktop's `getService` checks the service against the class it's given, which holds while the app and Terminal load one copy of the protocol package, as one install at the module's exact version does.
    Every instance carries a brand under a symbol all copies share, `Symbol.for`, so a check that meets a service of another copy throws a `PackageCopiesException` that names the cause, rather than failing as a wrong type.
  - It moves to a package of its own only if the maintainer ever wants one.

- An owner is a string the app chooses, from 1 to 256 UTF-16 code units, which Terminal only compares; it starts with the app module's id, such as `example.chat/42`.
- The app's window part provides the window's owners with `TerminalOwners.provide(context, newOwner)`, which returns the window's `TerminalOwners`; a window takes one provider, as `TerminalStartFolder` does, and `owners.removeAsync()` hides every owned terminal and lets another provider in.
  `newOwner` gives the owner a terminal from Terminal's own entries takes, or `null` for none, and is called at each open, so it follows the app's own setting; one that throws, or gives an owner that is blank or too long, opens a general terminal, which the app's log says.
- `owners.showAsync(owner)` shows that owner's terminals in this window, in the order they opened, and hides every other owner's; `owners.showAsync(null)` hides every owned terminal.
  The window starts with none shown, so after a reload it reopens only the general tabs, and the app shows its current owner again.
  Each window shows its own owner, and the shows run in the order asked.
  The owners' requests and log go through the app's context, and the tabs open and close through the terminal part's, since a part opens and closes only its own module's views; the part shares its context while it is active (`TerminalPart`), and the launcher uses it too.
  While the part isn't active, or once the part a show began with stops, the show only sets the owner and opens or closes no tab, and the part opens that owner's tabs as it activates; a launch whose part stops while the runtime launches opens no tab.
- A hidden terminal loses its tab, which Terminal closes through `closeView`, so Noldova Desktop doesn't report a person's close and the shell keeps running.
  Its pane detaches, so it never holds the shell back ([Flow control](#the-runtime-part)), and the runtime keeps its output: the screen in the mirror and the lines that leave it in the stored lines, under the same Output limit as a shown terminal's.
  Shown again, it opens where Noldova Desktop chooses, and its pane attaches to the screen it has and pages in what ran meanwhile.
- `terminal.new` takes an `owner` argument: a string ties the terminal to it, and leaving it out or `null` opens a general one; `takesNewOwner: true`, which can't come with an owner, ties it to `newOwner`'s.
  - Ctrl+Shift+\` and the View menu's New Terminal open a general terminal, whatever the app's setting.
  - The tab row's + passes `takesNewOwner`, and Toggle Terminal's first open takes `newOwner`'s too, so they follow the app's setting; the shell menu's rows open a general terminal with the chosen shell.
  - An app's own entry opens a terminal for a given owner by running `terminal.new` with `{ owner, tabGroup }`, such as a New chat terminal entry.
  - A terminal opened for an owner the window doesn't show opens hidden; from + or the first toggle, whose owner the app's `newOwner` gives, the app's log says so, since the person sees nothing open.
  - A new tab waits for the terminal list, which the runtime answers from what it holds; one whose owner stopped showing meanwhile, or whose terminal the runtime closed meanwhile, doesn't open, since the hide or close found no tab.
- An owner's terminals close two ways, each as closing their tabs does, ended terminals included:
  - the app's window part calls `owners.closeAsync(owner)`;
  - the app's runtime part calls `closeAsync(owner)` on the runtime service `terminal.owners`, which it gets with `context.getService("terminal.owners", RuntimeTerminalOwners)`; this works with no window open.
  Both reach the runtime's `terminal.closeOwner`, which unbinds the agent sessions bound to the owner at once, ends its terminals, forgets the ones kept for the next run, and sends `terminal.closed` for each, so every window closes that terminal's tab. A restore under way, and an open or run under way for that owner, finish first, so the terminals they bring close too, while another owner's opens and runs don't hold the close; an agent's open after the close starts takes no owner, unless its session's `terminal.owner` binding names it, which an app ends with the session.
- Closing an owned terminal's tab ends it, as for every terminal.
- The panel's terminal never has an owner. Toggle Terminal and Restart reach only terminals the window shows.
- The runtime keeps the owner: `terminal.open` takes it, `terminal.sessions` lists it, and the terminals' table keeps it across runs, through the migration `add-terminal-owner`, so a restored terminal keeps its owner.
  An agent's terminal has an owner only when the app bound its agent session to one ([Which terminals an agent reaches](#which-terminals-an-agent-reaches)); it isn't kept for the next run.

### Running an app's commands

An app's window part runs the person's commands from its own content in a terminal of an owner with `owners.runAsync(owner, command, folder, shellKinds)` ([INTEGRATION.md](INTEGRATION.md#running-commands-in-an-owners-terminal)).
It types into a terminal the person sees, so a change to which terminal it picks or what it types is a risky change.

- The window sends `terminal.run` through the app's context with the owner, the commands, the folder or the app's start folder, the kinds, the Default shell setting's shell, the opening size and the Output kept per terminal setting.
  `TerminalRunParams` checks each field as the other requests do; the commands are not blank, at most 16,384 UTF-16 code units, the limit of an agent's command, and hold no control character but line breaks and tabs, so they can't hold a paste's end or the integration's marks, and no format or default-ignorable character, Unicode category Cf or property Default_Ignorable_Code_Point, such as the bidirectional marks, the zero-width characters, the soft hyphen, the byte order mark, the variation selectors, the Hangul fillers and the tag characters, so a code block can't read differently from what runs; emoji are taken out first, so an emoji's joiners, variation selectors and tags pass. A refused field throws `RunArgumentRefusedException`, a `TerminalRunRefusedException`, in the window, naming it, and a hidden character by its code point, and nothing opens.
  The runtime never logs the commands or keeps them apart from what the terminal shows, and a refusal never holds them.
- The runtime takes the newest terminal of the owner, of one of the kinds or of any for none, that the connection reaches and that is free: a person's terminal, not an agent's, not ended or restarting, with no run waiting to type, whose shell has the integration's marks, whose prompt line is empty after the prompt's end mark and where the shell has read every key: keys typed at a prompt are read once a command started or ended after them and the shell waits at a new prompt, so a run right after the person's command ended at its prompt types at once. Output alone doesn't show it, since a line editor such as PowerShell's echoes typed text in parts, and a redraw of the prompt, changed or not, as an async theme's or a resize's, doesn't either, so a key at the prompt the shell still shows keeps the terminal busy for the echo's settle, a second, at most. So do keys typed while a command ran, after a line entered at the prompt but before its command started, or after a line break in the same paste, which the shell reads only after it draws the next prompt. A pane's reply to the shell, such as the focus report a window sends as the person clicks the app's Run, never echoes and counts as no key.
  A run's end comes at its command's end mark, before the shell draws its next prompt, which in bash follows the person's own `PROMPT_COMMAND` hooks and can take as long as they do. So when the newest such terminal is drawing its prompt, from a command's end or a prompt's start mark to the prompt's end mark, the run waits up to 10 seconds for the prompt, holding the terminal as a run that is starting, and takes it if it is then free; otherwise it takes the newest free one, or opens one.
  While the owner's terminals or the connection's are closing, a run that names none types nothing and answers `Ended` naming the newest of them. When there is none yet, as while the owner's only terminal is still opening, a run caught by its owner's close waits for the close to end and then runs as usual, in a new terminal, and a run whose own connection is closing fails at once and opens nothing, since no one is left to get its answer. A run already under way when the close starts, which the close waits for, opens nothing during it either: it stops, and then waits and runs again as a run sent during the close does. It checks the close once more right after opening a terminal, so a close that starts while its terminal opens gets `Ended` naming that terminal, which the close then closes.
  A shell without the marks can't be told free: its prompt and what was typed can't be told apart.
  So a Command Prompt is never free, and each run with `[CommandPrompt]` opens a new terminal, by design.
  Telling an idle Command Prompt from a busy one would need marks in its prompt, and it draws its prompt from its `PROMPT` variable, which every program it starts inherits, so the marks would hand those programs the integration's nonce.
  Running each command in a Command Prompt of its own instead would lose the shell's state, multi-line input and the terminal's look.
- With none, it opens a terminal for the owner as `terminal.open` does: the Default shell setting's shell, else the runtime's default, when that is of the kinds or none are given; else the first shell of the kinds the locator lists, installed shells before the WSL distributions. A folder that no longer exists opens the home folder, with the note `terminal.open` writes.
  With kinds and no shell of them installed, it opens nothing, types nothing and answers `NoShell` with no terminal: a shell of another kind would read the commands differently, so a `bash` block never goes into PowerShell. With no kinds and no shell at all, the open fails as `terminal.open`'s does.
- A terminal it opens is sent to the requesting connection's windows as `terminal.opened`, so a window that shows the owner opens its tab, and while a window that reaches the terminal shows its owner, by `terminal.showOwner`, its shell starts only at the first `terminal.resize`, which the pane's first fit sends, at that size, even one that changes nothing. What the pane sends before then is dropped, keys and pastes too: it would reach a shell still starting, and the pane's replies, such as a focus report, would show there as typed text; the first fit comes with the pane's first frame, so only what is typed that early is lost. A pane that isn't shown, such as one in a collapsed panel or a hidden tab, has no size to fit, so its first fit sends the terminal's own size instead, and a hidden window, which draws no frame for a fit, shows no owner to the runtime: the shell then starts at the size it opened with, as a terminal started in the background does, and the pane's fit resizes it once it shows. A shown pane too small for one row starts the shell at the smallest size, at least one column and one row, as the fit add-on clamps too, and its fit resizes the shell as the pane grows; a shown pane whose fit can't measure it, as before its first frame lays it out, sends nothing and waits for the next. Each time a pane attaches it sends its next fit's size again, even one that changes nothing, since a fit sent before the attachment never reached the runtime. When no such window shows the owner, since no pane will show the terminal, the shell starts at once at the 80 columns and 24 rows it opened with, and it starts so too once the last such window shows another owner or none, closes, or detaches the terminal's pane before the fit. A run without a tab waits for the asking window's fit instead, and starts at once while that window is hidden, since a hidden window draws no frame for the fit, or when it hides, closes or detaches the pane first. A run waits for either fit up to 10 seconds; then the shell starts at the size it opened with, as when no window shows the owner, and a pane's later fit resizes it, as for a shell started without a window. The runtime types once that shell's prompt is ready.
  - The shell starts at the fit because a shell that draws its prompt at one width and is then resized can draw what is typed next at the old width. Typed before the fit, a prompt longer than 80 columns wrapped there, and the pane drew the commands on the next line. Typed after a resize at the prompt, bash 5.3's readline still placed the command as if the screen were 80 columns wide, over the end of its prompt, however long the runtime waited after the resize. Started at the pane's size, the shell never sees a resize before the commands. A pane that fits a terminal whose shell started without a window showing its owner resizes the shell already running at 80 columns, and the commands typed after it can still be drawn at the old width; the runtime doesn't wait for the shell's next prompt there.
  - Until the shell starts, what the pane sends, such as its answers to queries no shell asked, is dropped, and a key the person types counts as typing before the commands, so they aren't typed. A close, or the runtime's end, before the start answers `Ended` and starts no shell; a shell that can't start is logged, and its terminal shows its exit.
- It types the commands once the shell shows its prompt, as an agent's first command waits: line breaks at the end dropped, the others as Enter, inside `ESC[200~` and `ESC[201~` when the shell turned bracketed paste on, as the mirror reads it, then Enter. The typing counts as the person's keys, so a second run before the shell read it opens another terminal rather than adding to the first's line; the later lines of a paste without bracketed paste are typed ahead of the first line's command, so only the settle ends them.
- Right before it types, it checks again, and types nothing when the terminal ended, closed or restarted meanwhile (`Ended`), when a key came since the pick (a key of the person's or another run's typing, and for a terminal it opened only the person's; never a pane's reply to the shell, such as a focus report) or, for a shell with the marks, the prompt line holds text (`Input`), so the person's keys never join the paste, or when the commands hold a tab and the shell hasn't turned bracketed paste on (`Tab`), since the shell would take it as completion.
- It answers once it has typed or given up, with a `TerminalRunResult` of the terminal and that outcome, since a request's failure reaches the window without its reason. A new terminal's tab opens before the paste, so a key the person types into it first answers `Input`.
- For `NoShell` the window throws `RunShellKindsMissingException`, a `TerminalRunRefusedException` for `shellKinds`, naming the kinds, and opens no tab.
- The window then shows the terminal's tab and gives its pane the focus while it still shows the owner (`TerminalFocus.showAsync`), else opens its tab, which takes the focus as a new tab does; a terminal of an owner the window doesn't show opens hidden, and its tab opens when the owner shows. For any outcome but `Typed` it then throws `TerminalRunNotTypedException` with the terminal and the outcome.
- A typed run gets an id, a UUID, in the answer, and the terminal keeps, for its latest 100 runs, the mirror's line where the run's prompt started, or the cursor's line for a shell that has drawn no prompt with the marks yet. A line's number counts every line that left the screen's top before it, so it stays the line's own while lines leave above it; a resize that changes the columns reflows the screen and moves the lines, so each kept line has an xterm marker on it, and the mirror numbers it again from its marker after each resize. A line xterm trims keeps its last number, and the terminal disposes a run's marker when it forgets the run, as the session does its prompt's when the next prompt starts or the shell restarts.
  The mirror numbers each line of the normal screen by every line that left the screen's top before it, stored, erased with the saved lines or reset away, so a run's line keeps its number while later output scrolls it into the stored lines.
  The session splits what it hands the mirror at each prompt's start mark and asks the mirror for the line once it has parsed up to there, so the number is the prompt's own line however the output arrived.
  A restart forgets the terminal's runs, since its new shell's lines no longer follow theirs.
- `startRunAsync` with a target sends the terminal's `sessionId` and `whenBusy` in `terminal.run`.
  The runtime takes only that terminal, if it is a person's terminal of the owner, of the kinds, that the connection reaches; for any other it types nothing and answers `Ended`, as for a terminal that closed, so a connection learns nothing of terminals it doesn't reach.
  A target drawing its prompt is waited for first, up to 10 seconds, as an untargeted run waits, so a run sent right after the last run's end types once the prompt is drawn; the wait ends when the terminal closes. A target whose owner's terminals or connection's are closing answers `Ended` at once and types nothing. A target that isn't free, or that another run is still starting in, is busy: `Refuse` answers `Busy` at once; `Interrupt` waits up to two seconds for a command to start and to hold the terminal, since a Ctrl+C the shell gets instead is lost (PowerShell loses one while it still reads the typed line, and zsh and bash mark a start before they start the command, so on Linux and macOS the runtime waits until the terminal's foreground process group, which Noldova Desktop's pseudo-terminal reads, is no longer the shell's; bash and zsh also give the command's new group the terminal before its program starts, and a copy of the shell in that moment loses a Ctrl+C, so the runtime also waits while the group's leader has the shell's own program and command line, and once the two seconds pass with a copy still holding the terminal, as a subshell such as `( sleep 30 )` does for its whole run, it sends Ctrl+C anyway), writes Ctrl+C to it, waits up to two seconds more for the shell to be free, then types as any run does, or answers `Busy`; a line that doesn't start, such as one the person is still typing, gets no Ctrl+C.
  A run that waits marks the terminal as starting a run until it typed or gave up, so a second run at the same time answers `Busy`, and an untargeted run doesn't pick that terminal.
- `startRunAsync` with `shown` sends `opensTab: false` in `terminal.run`, for an app that shows the run's terminal in its own pane, such as under a chat's code blocks, where a panel tab taking the focus would take it from the chat.
  The runtime picks or opens the terminal as for any run, then, before it types, sends `terminal.runOpened` with the terminal's `sessionId` to the asking window alone, through the event channel's `publishTo` with the request's connection and window, since another window has no run under way to take it; with a target the window already knows the terminal and calls `shown` before it sends the run.
  A terminal it opens remembers it opened without a tab, and its `TerminalSummary` says `opensTab: false` in `terminal.opened` and `terminal.sessions`, so no window opens its tab when the event comes, when its owner shows or when the window part activates; the runtime keeps the mark with the terminal for the next run, a terminal an earlier version kept reading as opening its tab; it stays in the window's list and the agents' tools, and its tab opens only when the person opens it there. A free terminal it picks keeps its own mark.
  `shown` attaches the app's pane, whose first fit starts the new terminal's shell at the pane's size, as a tab's does; while the window is hidden, or when it hides, closes or detaches the pane first, or once the pane hasn't fit within 10 seconds, the shell starts at 80 columns and the run still answers.
  The window runs its runs with `shown` one at a time, so the one `terminal.runOpened` it waits for at a time belongs to the run under way; runs without `shown` don't wait for them, and an event that comes with no run waiting is dropped. Should the event not have come by the run's answer, the window calls `shown` once with the answer's terminal.
- `terminal.runOutput` gives a run's lines, from its prompt's line up to the next run's in the same terminal, or up to the cursor's line for the latest: the last ones up to the limit asked, from a line's start, so a cut never begins inside a wrapped line, and the number of earlier lines cut, by the limit or because the mirror's screen and its 1,000 lines of scrollback no longer hold them; the stored lines aren't read, as their numbers aren't kept.
  Only the app's connection reads it, and only from a person's terminal, so a run's output never reaches an agent, as an agent never reaches a person's terminal of an owner ([Which terminals an agent reaches](#which-terminals-an-agent-reaches)); no agent tool calls it.
  It answers `null` alike for a run it can't give, and the window throws `TerminalRunNotFoundException`, since a request's failure reaches the window without its kind.
- A typed run waits for its end, which only the asking window hears, through `publishTo` with the request's connection and window, as `terminal.runEnded` with a `TerminalRunEnded`.
  The run needs one command end for a paste the shell took whole, with bracketed paste, else one for each line; a command ends at its end mark, or at a prompt that starts on a new line without one, as a launch's command does, and the prompt right after an end mark ends nothing more.
  The run ends as `Command` with the last of those ends' code; as `TerminalEnded` when its shell exits or restarts, its terminal closes or the host ends first; and as `NoIntegration` at once in a shell without the integration's marks.
  The next run typed into the terminal ends a run still waiting first, as `Command` with its last counted code, since its shell took the next one at its prompt.
  The answer to `terminal.run` carries in `endedRuns` the ends known as the run was typed, the run before's and the run's own `NoIntegration`, for the asking window, since the event may reach the window after the answer; a run of another window hears of its end by the event.
  The window's `TerminalRunEnds` keeps an end that comes before its run's answer, the latest 64, and gives each run's `ended`; a runtime that starts again ends every run still waiting as `TerminalEnded`.

Another module adds entries to the new-terminal menus as Noldova Desktop's `documents/MODULES.md` ("Menus and toolbars") lets a module that declares `terminal` as a dependency: a group in the tab row's place `terminal.tabRow`, after Terminal's + and shell menu, or in the shell menu `terminal.shellMenu`, after the shells.
Each item runs one of its own commands, which Noldova Desktop gives the tab row's `tabGroup`.
Both places are part of Terminal's public API.

## The agent tools

The runtime part registers seven tools with Noldova Desktop's tool registry through its context's `tools`, in `src/noldova.terminal/src/tools/`, as `module.json` declares them under `contributes.tools`, and withdraws them when it deactivates.
Each tool's risk is fixed, and the module never parses a command to change it.
`terminal_list` and `terminal_read` are read-only; the others mark when they begin to send input, and `terminal_open`, `terminal_write`, `terminal_interrupt` and `terminal_close`, which aren't resumable, name the tool that tells where things stand after an uncertain end: `terminal_list` after an open or a close, `terminal_read` after keys or an interrupt.

| Tool | What it does | Risk | Resumable |
|---|---|---|---|
| `terminal_list` | Lists the terminals the agent session may use. | Low | Yes |
| `terminal_read` | Returns a terminal's output since the session's last read, waiting up to 30 seconds for more. | Low; Medium in a terminal the person shared | Yes |
| `terminal_open` | Opens a terminal in the session's working folder. | Medium | No |
| `terminal_run` | Runs a command at a terminal's idle prompt. | High | Yes |
| `terminal_write` | Writes keys to a terminal, such as an answer to a prompt. | High | No |
| `terminal_interrupt` | Interrupts what a terminal runs. | Medium | No |
| `terminal_close` | Closes a terminal. | Medium | No |

### Which terminals an agent reaches

- An agent session reaches the terminals it opened and the ones the person shared with it; to every other terminal, the tools answer as if it did not exist.
- The app binds to each agent session, as it opens it with `openSession(scope, bindings)`, its working folder as `terminal.folder`, an absolute path, and the terminals the person shared with it as `terminal.shared`, a list of terminal ids; a call whose session's bindings the tools can't read fails as `Refused` with `terminal.invalidBinding`.
- An app ties an agent session to an owner, such as the chat whose agent it runs, with the binding `terminal.owner`, the owner, as it opens the session, or with `bindAgentSession(agentSessionId, owner)` on the runtime service `terminal.owners`, which takes over the binding until `unbindAgentSession(agentSessionId)` unties it; that one goes when the session ends.
  A `terminal.owner` that isn't a string, is blank or is longer than 256 UTF-16 code units fails the call as `Refused` with `terminal.invalidBinding`. Closing the owner unbinds the sessions `bindAgentSession` bound, but not a session's binding, which stays for the session's life.
  - The terminals a bound session opens take its owner, so they are the owner's terminals in every window ([Terminals with an owner](#terminals-with-an-owner)): the runtime sends `terminal.opened`, so each window that shows the owner opens its tab, which never takes the focus, so what the person is typing elsewhere, such as a message, never goes into the agent's shell; the person watches the agent's commands live, types into the terminal, interrupts it and closes it, and closing its tab ends it. An agent's `terminal_close` sends `terminal.closed`, so every window closes its tab. Restart stays refused, since the agent started its shell.
  - A bound session also reaches every agent's terminal of its owner, whichever of the owner's sessions opened it, one running at the same time included, so the chat's next turn finds the terminal the last one left; it doesn't reach the person's own terminals of that owner unless they were shared with it.
  - The tools keep their permission requests and their checks of the prompt, which count the person's keys as they reach the terminal, before the shell echoes them: a terminal whose keys from the person the shell may not have read isn't idle, so a `terminal_run` there is refused even when the person allowed it always. Idle means the prompt line is empty after the prompt's end mark and the shell has read every key, as for an [app's command](#running-an-apps-commands): keys typed at a prompt are read once a command started or ended after them and the shell waits at a new prompt, and until then the echo's settle, a second after the last key, bounds the wait. Output alone doesn't show the keys were read, since PowerShell's line editor can first send only cursor moves and colors, which leave the line empty, before the typed text reaches it; so a key that never echoes, or a cursor move or a bell that leaves no text, holds it a second. A new prompt with no command after the keys, as after Ctrl+C, holds it too, since a redraw of the prompt can't be told from it. A pane's reply to the shell, such as a focus report, doesn't hold it, and without the shell's integration, where a background job's output can't be told from an echo, it lasts the whole second, and a line the person typed while a `terminal_run` waited for its grant fails the run as `Stale`, while a pane's reply to the shell, such as the focus report sent as the person clicks Allow elsewhere in the app, doesn't. A call whose session lost the terminal while its request waited, such as by its binding going, fails as `Stale` too.
  - A binding made after the session ended stays until `unbindAgentSession`, since the tools heard of the end before it.
- Commands run in the terminal's persistent shell, so a folder or a variable one command sets holds for the next.
- Each tool that acts on a terminal declares one call per resource, keyed by `/terminal_id`, and the registry gives the turns: a call from the same session waits in order, its wait counting against its own deadline; a call from another session fails at once as `Unavailable`; calls on different terminals don't wait for each other.
- `terminal_list`, `terminal_read` and `terminal_open` run in parallel.
- When the session ends, the tools close the terminals it opened without an owner and leave the ones with an owner and the shared ones open; a terminal with an owner closes when the person closes it or the owner closes.

### The permission request

Each tool but `terminal_list` raises its own request before any side effect, through its call, as Noldova Desktop's `PERMISSIONS.md` says, and acts only on `allowedOnce` or `allowedAlways`. `terminal_list` is read-only at a low risk, so Noldova Desktop raises no request for it.
Noldova Desktop takes the session and the scope from the call, sends the request to the app's answerer, keeps an always answer, and denies every request while the app has no answerer.

| Action | Tool | Title | Subject |
|---|---|---|---|
| `terminal.read` | `terminal_read` | Read a terminal's output | The JSON array of the terminal's id |
| `terminal.open` | `terminal_open` | Open a terminal | The JSON array of the shell's id, `null` for the default shell |
| `terminal.run` | `terminal_run` | Run a command in a terminal | `sha256:` and the hex SHA-256 of the JSON array of the terminal's id, its folder and the command |
| `terminal.write` | `terminal_write` | Send keys to a terminal | `sha256:` and the hex SHA-256 of the JSON array of the terminal's id, its folder and the keys |
| `terminal.interrupt` | `terminal_interrupt` | Interrupt the program running in a terminal | The JSON array of the terminal's id |
| `terminal.close` | `terminal_close` | Close a terminal and end its shell | The JSON array of the terminal's id |

- Each request but `terminal_write`'s offers allow once, allow always and deny, at the tool's risk; a low-risk `terminal_read` of the session's own terminal lets the app's policy answer without asking the person.
- `terminal_write` offers only allow once and deny: keys answer whatever the program asks, which no subject can hold, so allowing `y` and Enter for one question must not answer a later one; Noldova Desktop applies a remembered answer by its subject alone, whatever a later request offers, so a write never offers one to remember.
- Its details are labeled: the terminal's title, id and whether the person shared it; for `terminal_run` and `terminal_write`, the shell and its program; the working folder, a one-shot's being the one its shell started in, or that it is unknown, and whether it lies inside the session's working folder; the command or keys, escaped, and whether they hold characters that hide or reorder text; for `terminal_run`, that it runs at the shell's prompt, or the one-shot program line; for `terminal_write`, whether the terminal waits at an empty prompt; and the agent's explanation, as its own words.
  Text that reaches the terminal exactly, the id, the program, the folder, the command, the keys and the program line, is `code`.
  The title and the folder, which a program in the terminal can set, show their control and hidden characters escaped, and their backslashes as they are.
- `denied` and `deniedAlways` fail the call as `Denied`, `expired` as `Expired`, `withdrawn` as `Withdrawn`, and any other decision as `Denied`.
- A request whose details would be more than Noldova Desktop's 80 KiB as JSON, such as a one-shot of 16 KiB of backslashes, which its escaped command and its program line both show, fails the call as `Refused` with `terminal.requestTooLarge` before it is raised.

1. The tool checks the terminal first: running, and for `terminal_run` idle at an empty prompt, where the shell has read every key the person typed; for `terminal_write`, not waiting for a password, and with no line the person is typing.
2. The request shows what the grant allows: the exact command or keys with control, bidirectional, zero-width and other invisible characters escaped, such as the soft hyphen, the line and paragraph separators and the tag characters, the terminal, its shell, and its working folder taken only from the shell integration's verified marks, with whether it lies inside the session's working folder.
3. `terminal_run` offers allow once, deny, and always for the exact bytes in that folder; `terminal_write` offers no always.
   An always grant keeps the terminal's id, so it never reaches another terminal; for `terminal_run` it also stays tied to the exact text and folder, through the subject's hash.
4. On a grant, the runtime checks that the terminal's prompt is still the one the request showed and writes, in one synchronous step; a changed prompt fails the call as `Stale`, and nothing is written.
   A prompt the shell draws again is still the same prompt, as when a window's pane fits the terminal and bash's readline draws the prompt again, its marks included, at the new size; the person's line then starts after the new drawing.
   A prompt end counts as such a drawing only when no mark but one prompt start came since the last prompt end, and the text since then, after the drawing's own line end, is exactly the prompt's: whole when the drawing has its start mark, and only its last line when it has none, as readline draws only the last line of a prompt of several lines.
   A folder report, which each new prompt of bash, zsh and PowerShell in a file system folder sends first after any PATH report, a PATH report, a command's start or end, a second prompt start, other output, even only spaces or line ends, or other prompt text makes it a new prompt, and the call fails as `Stale`; so does every end of a prompt whose start mark never came, since its text is unknown.
   A new prompt with the same text and no command between therefore counts as new only through its folder report, as `agent-terminals.test.ts`'s "refuses to act on a prompt other than the one it showed" shows.
   Where no folder report comes, it counts as the same prompt: PowerShell outside a file system location, such as `HKLM:`, sends none, and neither does a prompt hook the person replaced.
   The person's own keys, an Enter at an empty line included, still change the prompt the request showed, since it holds the count of keys that reached the terminal, so a call after them still fails as `Stale`.
5. A terminal without shell integration runs the command as a one-shot `<shell> -c`, and the request says so and shows the program line it runs, quoted as node-pty passes it, with the command's backslashes as the shell reads them and only hidden characters escaped.

A password prompt is for the person: a terminal waiting for one refuses `terminal_write`, and every report says it waits.

Keys an agent writes join whatever waits on the line, so after the person types `rm -rf `, a write of `make` and Enter would run both.
`terminal_write` fails as `Unavailable` with `terminal.lineInUse` while the person typed in the terminal under the echo's settle, a second, ago, or, at the prompt of a shell with integration, text waits on its line, the agent's own included.
While a command runs, or without integration, the line can't be read, so only the settle tells.

### Commands and their output

- `terminal_run` returns after the command ends or after its yield, 10 seconds by default and from 0.25 to 30, and the command keeps running; `terminal_read` returns the rest.
- A command's own time limit ends it; 0 means none.
- At the prompt, a command ends with the shell's end mark, or, when the shell marked nothing for it, at the first prompt that starts on a new line after the shell echoed the command's line, without an exit code or working folder, its output up to that prompt. The first start or end mark after the typing is the command's, so a prompt between its start and end marks, as a nested shell's, doesn't end it, and a later command's marks aren't its. A prompt before the shell read the line, as after the person's Enter or a job notice, or one redrawn in place, doesn't end it, nor does a later one. The echo is the typed text's last line, read as the output comes, since the agent's text keeps only its latest part, and matched at the end of a line and without white space, since a long line wraps; a restart drops the lines typed into the old shell.
- A command interrupted by its time limit or by its call's end that gets neither within 2 seconds, as when the program ignores the interrupt, ends anyway, killed, with no exit code or working folder and the output it had then; the program may still run, and the terminal's prompt still tells whether it is free. `terminal_interrupt` only sends the interrupt key, so a program that survives it, such as a REPL, still reports running.
- A command still running when the person restarts its terminal ends there, killed, with no exit code or working folder and the output up to the restart: the old shell is gone, so nothing of the new shell's counts as its output, and stopping it sends nothing to the new shell.
- A report holds the terminal's title as the call returns, its name and its shell's name, how the command ran (at the prompt or as a one-shot), the status (running, waiting for input, exited or killed), the exit code, the working folder and at most 30,000 characters of output, the head and the tail, with the count left out; the log file keeps the output up to 16,777,216 characters, and a log cut there ends with a line that says so.
- `terminal_write`'s result holds the terminal's id and its title as the call returns, marked untrusted with the terminal's origin.
- Every report and result that holds the title, `terminal_open`'s, `terminal_list`'s entries, `terminal_run`'s, `terminal_read`'s and `terminal_write`'s, also holds the terminal's `name`, the person's or the app's name for it or `null`, and its `shell_name`, the name of the shell it runs. The window names a terminal's tab `name`, else the title an app launched the terminal with, else `shell_name` ([Session tab](#the-window-part)). The launch title stays in the window and no report holds it, so an app that launched a terminal with a title names it by that title itself, and otherwise by `name`, else `shell_name`. The report's title is the program's and can be a path, such as the console's on Windows.
- Terminal output and titles are untrusted text, and each result names its origin.

### Failures

A tool fails with one of Noldova Desktop's codes: `Refused`, `Denied`, `Expired`, `Withdrawn`, `Stopped`, `Cancelled`, `Stale`, `TimedOut`, `OutcomeUncertain`, `TooLarge` or `Unavailable`, and the module's own code, such as `terminal.notIdle`, says why.

- A terminal the session may not reach fails as `Refused`, and no request is raised.
- A call that ends while its request waits for the person fails as `Withdrawn`.
- A call that ends before any input reached the terminal, while it waits for its turn or after the grant, fails by the reason the runtime gives for ending it:

| Reason | Failure | The command an agent's run started, when `terminal_run` or `terminal_read` ends |
|---|---|---|
| The person stopped it | Stopped | Interrupted |
| The agent or the runtime cancelled it | Cancelled | Interrupted |
| The agent session ended | Cancelled | Interrupted |
| The tool was switched off | `Unavailable` | Keeps running |
| Its deadline passed | `TimedOut` | Keeps running |

- When `terminal_open` or `terminal_close` ends after it began to act, the outcome is uncertain, whatever the reason: it fails as `OutcomeUncertain` with `terminal.outcomeUncertain`.
  - A close still ends the terminal, once, as every close does; the cancel stops only the call's wait.
  - A terminal whose start completes after the cancel stays open, owned by the session, and `terminal_list` lists it, so the agent finds it again; the session's end closes it as usual.
- `terminal_write` and `terminal_interrupt` act in one synchronous step, so once they have acted they return success.
- `terminal_run` and `terminal_read` fail with the code of what ended the call and carry the output they had, and the next read starts from the same place.
  - Interrupting sends the interrupt key once at the prompt, or ends a one-shot, and the failure's output says the command was interrupted.
  - Noldova Desktop's registry ends a call at once when its signal aborts and drops the failure the tool gives after it, so for now the agent gets the code without the output, and the next `terminal_read` returns it.

### The boundary with the terminals

The tools reach terminals only through `IAgentTerminals`, which the runtime part's terminals implement.

- Each terminal keeps the text an agent reads: its output with escape sequences and control characters removed and line ends as `\n`, at most the latest 2,097,152 UTF-16 code units.
- An agent's terminal opens at 120x30 and waits for the integration's first prompt: up to 60 seconds once the integration's loaded mark came, and up to 10 seconds for that mark.
- With integration, a command is typed at the prompt and the marks give its output, exit code and working folder.
  Without it, each command runs as a one-shot `<shell> -c` in its own pseudo-terminal in the terminal's folder, and keys and interrupts go to it while it runs:
  - Command Prompt gets its own command line, `cmd /d /s /c "<command>"`, as it is, since a Windows pseudo console quotes an argument list by the C runtime's rules, which Command Prompt doesn't read.
  - A Command Prompt started with `/k`, as the Developer Command Prompt starts VsDevCmd, runs the command after the same start with `&&`, in a Command Prompt of its own, named by its full path since a bare `cmd` would find one in the terminal's folder first, so the variables the start sets read as set. The start runs without `call` and without delayed expansion, so its arguments arrive as `cmd /k` gives them: a caret and a `!` as they are, and a `%` variable expanded. The command comes in `NOLDOVA_TERMINAL_COMMAND`, which a Command Prompt with delayed expansion reads only after splitting its own commands, so the command's quotes and operators arrive as they are; the inner Command Prompt starts without delayed expansion, as at the prompt, and clears the variable before the command runs. A start argument with a space, a caret or an operator goes in quotes.
  - PowerShell gets `-NoProfile -Command`, after its start command, such as Developer PowerShell's Enter-VsDevShell.
  - A WSL terminal runs it in its distribution, `wsl.exe -d <name> -e sh -c <command>`.
- The first command an agent runs in a terminal opens the terminal's log file, owner-only on macOS and Linux, which takes the terminal's text and its one-shots' output from then on, up to 16,777,216 characters: at that limit the file ends with a line saying it stops there, and the module's log says so once; a write that fails is written to the module's log once and the file stops there.
- A terminal waits for a secret while its last line asks for a password, passphrase or PIN and ends with a colon. Only English prompts are recognized, so a prompt in another language reads as a command waiting for input.
- The runtime keeps the 32 latest ended terminals, so their text stays readable, and forgets older ones.

The tools' tests run their calls through Noldova Desktop's own tool registry, as the runtime part registers them.

        ▼                ▼
